# ADR-0022: Task-ID trailer 正则扩展——接受评估档 `D{nn}` 前缀

版本: 0.1 · 状态: **草稿（2026-09-26 起草）** · 关联: M-1-WP05
（追溯基建·commit-msg 钩子）、M6-D67（首个使用新前缀的评估档任务）、
AGENTS.md「提交与追溯格式」
负责人: @lead · 起草日期: 2026-09-26

## 背景

执行方案 §2 与 AGENTS.md「提交与追溯格式」规定所有非合并提交必须挂
合规 `Task-ID: M{m}-WP{nn}-T{nn}` trailer；该契约由本地
`scripts/hooks/commit-msg` 与 CI `scripts/check-task-ids.sh` 双重把关。

M6 阶段开始引入「评估档」任务（执行方案 §6.5/§7 的 D1–D7），其命名约定
为 `M{m}-D{nn}-T{nn}`——例如首个评估档任务 `M6-D67-T01`（D6 三推理栈
冒烟 + D7 公开数据集 IR 双档，SPEC 已批准，2026-09-26 commit
`c883656`）。当前正则仅匹配 `WP{nn}` 分支，故该提交必须用
`git commit --no-verify` 绕过本地钩子，且 CI 的 `task-ids` job 因 PR
而非 fork 不命中（合并前 hook 缺失已绕过，合并后追溯链仍残缺）。

**根因**：钩子正则（`scripts/hooks/commit-msg:6` + `scripts/check-task-ids.sh:9`）
在「评估档」概念落地之前已固化；评估档 = 阶段尾部的合规审计/性能基准/
数据集评测任务（执行方案 §6.5/§7.1/§7.2），与「工作包任务」同属铁律 2
「追溯唯一」覆盖范围，但用 `WP{nn}` 命名会在 WP 计数上无意义地占用
WP 序号（每阶段 1–9 WP 限已用尽）。

## 决策

将 Task-ID 正则从「WP 单一分支」扩展为「WP 或 D 双分支」，精确字面为：

```regex
^Task-ID: M-?[0-9]+-(WP[0-9]{2}|D[0-9]+)-T[0-9]{2}$
```

`$` 端锚为顺手修复：旧正则 `T[0-9]{2}` 在 `T123` 类子串误匹配（`T12`
前缀即放行）；新正则以行尾严格收尾，杜绝「`Task-ID: M0-WP01-T123`」
这类 typo 蒙混过关。

约束不变：

- 阶段号仍允许 `M-1` 前缀（保留 `M-?` 量词，覆盖 `M-1-WPxx-Txx`）
- WP 与 D 互斥：`WP` 后必须两位数字，`D` 后允许多位（`D67`/`D123`）
- 仍位于提交 body 行首（`^`），合并提交豁免（commit-msg 已有）

落地点（精确 diff）：

```diff
# scripts/hooks/commit-msg
-pattern='^Task-ID: M-?[0-9]+-WP[0-9]{2}-T[0-9]{2}'
+pattern='^Task-ID: M-?[0-9]+-(WP[0-9]{2}|D[0-9]+)-T[0-9]{2}$'

# scripts/check-task-ids.sh
-pattern='^Task-ID: M-?[0-9]+-WP[0-9]{2}-T[0-9]{2}'
+pattern='^Task-ID: M-?[0-9]+-(WP[0-9]{2}|D[0-9]+)-T[0-9]{2}$'
```

PR 检查单新增项：「若提交 trailer 含 `D{nn}`，确认 SPEC 位于
`docs/specs/M{m}-D{nn}.md` 且已批准」——与现有 WP 检查对称。

## 备选方案

| 备选 | 评估 | 否决理由 |
|------|------|----------|
| **A. 扩展正则接受 `D{nn}`**（采纳） | 5 行 diff，覆盖 `M6-D67` 与未来 `M6-D6/D7` 等所有评估档任务 | — |
| B. 评估档任务继续走 `M{m}-WP{nn}-T{nn}` 命名 | 零代码改动 | WP 序号虚假占用（`WP67` 不存在语义）；M6-WP67 会被误解为第 67 个 WP；铁律 2 要求 Task-ID 与 SPEC 一一对应 |
| C. 评估档完全豁免 Task-ID trailer（CI 单独名单） | 不动钩子 | 破坏追溯唯一性；评估档恰是审计抽样目标，必须可追溯 |
| D. 引入第三分支 `M{m}-AUDIT{nn}-T{nn}` 语义化命名 | 命名更显义 | 与执行方案 §7.1「D 档 = 审计/评估」既有命名约定冲突；徒增第三条分支后续维护成本 |
| E. 用正则 `\bWP\|D\b` 简短写法 | diff 更小 | 边界语义过宽（`XYZWPD` 类误命中）；精确两组显式更安全 |

## 后果

正面：

- `M6-D67-T01` 类提交免去 `--no-verify` 绕过（钩子自然放行），CI 的
  `task-ids` job 不再为 fork PR 漏检
- 执行方案 §7「评估档」概念与追溯契约对齐，铁律 2 单一规则覆盖所有
  任务类型
- 后续 M7+ 评估档（基线回归审计）天然合规

负面 / 放弃：

- 正则长度增加 16 字符（`WP[0-9]{2}\|D[0-9]+`），可读性轻微下降（已
  用括号分组与注释缓解）
- 钩子新增第二语义分支，未来若出现第三类任务（如 `M{x}-EXPLORE{nn}-T{nn}`
  探索档）需再开 ADR 扩展——已在「重新评估条件」登记触发器

无新依赖；无 deny/audit 影响（纯 bash 正则）。

## 重新评估条件

以下任一信号出现必须复议本 ADR 并可能再起扩展：

- 出现第三类任务命名约定需求（`EXPLORE`/`INCIDENT`/`SPOF` 等）→
  评估是否统一为「任务类别枚举」表 + 工具生成正则
- 执行方案 §6/§7 的 D 档语义再次细化（如 D 档拆分为 `D-AUDIT` 与
  `D-EVAL`），需重审正则是否需子类型
- 任何「豁免 Task-ID」的请求出现 → 拒绝并要求本 ADR 重新评估
