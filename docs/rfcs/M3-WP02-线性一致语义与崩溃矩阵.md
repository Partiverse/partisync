## 1. 范围与结论总览

覆盖：单分片读写的线性一致语义、跨分片/跨平面顺序、故障切换承诺、
分裂×复制耦合的崩溃矩阵。**不覆盖**：跨分片分布式事务（永久出界，归
应用层）、WP03 对账、数据面 WP04。

结论（先行）：

| 语义面 | 承诺 | 实现锚点（均为 Replica 层，Hub 门面未接线） |
|---|---|---|
| 单分片写 | 线性一致（raft commit → apply → ACK） | `Replica::write`（client_write）/ `submit`+`WriteHandle`（流水线） |
| 单分片读（leader） | 线性一致（ReadIndex） | `Replica::linearizable_read`（`ensure_linearizable` + 本机 SM 读） |
| 单分片读（follower） | 每副本内顺序一致（§3.2 定义与作用域） | `wait_applied` + `read_applied`（裁定 F1，定义于 §3.2） |
| 跨平面（entry/children） | 无事务，投影允许短暂陈旧 | WP01 §5 保持；同组同 log 两段 SM（裁定 7）保证复制顺序一致——**业务平面经 raft apply 未接线**（raft_store 仅为通用存储面） |
| 跨分片 | 无事务、无全局顺序 | WP01 §5 保持；每分片各自线性一致 |
| 故障切换 | 已 ACK 写入不丢；ACK 前崩溃 = 未提交（客户端超时语义） | raft 日志批 fdatasync（raft_store durability）+ raft 承诺 |

## 2. 术语与机制基础

- **线性一致**：读返回值落在实时序（real-time order）内最后一次写之后
  （Lamport 定义）；本文中 leader 读经 ReadIndex 满足。
- **顺序一致**：各副本观测到的操作序与程序序一致，不要求实时性。本文
  中 follower 读仅在**单副本内**满足（§3.2）。
- **blank entry（leader 就任 noop）**：openraft 新 leader 就任即追加一条
  blank 日志（engine leader_handler：`read_log_id = max(noop_log_id,
  committed)`）。该条目是 ReadIndex 可见性论证的承重件：新 leader 的读
  确认点不低于其 noop 条目，而 noop 之前已 commit 的写必含于其 log。
  **索引算术约束**：log index 空间含 blank 条目，任意「ACK 序列 = 线性
  索引序列」的测试假设仅在「写相位内不发生改选」时成立（blank 落在
  读写区间之外）；改选后索引需重新锚定（以 `client_write`/`ack` 返回
  的 log index 为准，不做算术推导）。
- **single-term-leader 特性未启用**：`CommittedLeaderId` 携带
  leader node id——LogId 全身份（term+node+index）参与 openraft progress
  匹配（T05 教训：日志编码丢 node 触发 follower log reversion 断言，
  `57f76fc` 修复）。

## 3. 单分片路径

### 3.1 写路径（线性一致）

`Replica::write` → openraft `client_write`：leader 追加日志（fjall 批
fdatasync 后 ACK 日志，`raft_store::append`）→ 复制至 quorum → commit →
三节点各自 apply（`RaftStateMachineStore::apply`：数据节按 log index
upsert + 应用指针/membership 同批 fdatasync）→ 应答返回 log index
（ACK 时刻 = 本条目已 apply 于 leader 状态机——openraft
`handle_apply_result → send_response`）。

**线性一致论证**：客户端 ACK 时刻该写已 apply 于 leader；任何后继读
（a）同一 leader：ReadIndex 确认点 ≥ read_log_id = max(noop, committed)
≥ 该写，且等待本机 apply 追平后返回（§3.1 引用 openraft
`ensure_linearizable`）；（b）新 leader：raft 承诺新 leader log 含全部
已 commit 条目，其 noop 条目保证确认点不低于旧 commit 线。`HubData`
newtype-over-bytes 不影响顺序语义。

**重复提交**：客户端超时后重试同一载荷 = 新 log 条目（openraft 不做
应用层去重）。**请求 id 目前仅为调用方约定，无任何系统机制承载**——
幂等去重归 WP03 对账窗口（本 WP 不引入）；在机制落地前，重复写入由
调用方以同键 upsert 收敛（WP01 put 语义）。

### 3.2 follower 读（每副本内顺序一致，裁定 F1）

follower 读 = `wait_applied(target_index)` + `read_data_row`。**定义与
作用域**：调用方指明目标 log index（如刚在某 leader 上 ACK 的值），
等待保证本机 apply 追上该点后读取。由于数据行按 index 不可变、本机
apply 单调前进，**同一副本内**连续读单调（不回退）。**边界**：客户端
混用 leader 读与 follower 读时，follower 目标滞后于 leader 最新提交会
观测到「回退到旧值」——此时全局不满足线性一致也不满足跨副本顺序一致；
调用方须以**递增 log index 作为会话序**约定（每次读的目标 index 非降）
方可成立。

**裁定 F1**：v0.1 follower 读仅暴露上述顺序一致形态；**线性一致
follower 读（SPEC 验收 4 之「follower 经 ReadIndex 读不返回旧值」）本
WP 未交付**——0.9.25 `ensure_linearizable` 仅 leader 可用（engine
`leader_handler` 门禁，进场核实），follower 不自动转发；补齐需
follower→leader 的 read_log_id 转发或 lease read，均引入新故障面，移交
WP03+（见 §7 对账表）。T07 基准口径按 leader 读计。

### 3.3 读确认时序约束（工程注记，机制勘误）

**机制（源码锚点）**：`ensure_linearizable` 的 quorum 确认轮超时
（ttl）= **heartbeat_interval**（openraft raft_core.rs:308），在此窗口
内若无任何 follower 应答，返回 `QuorumNotEnough{got:{self}}`
（granted 集初始只含自身）。follower 以更高 vote 应答时走 HigherVote →
ForwardToLeader 分支——**「新 term 打断」产生的是转发错误而非
QuorumNotEnough**。

**实测观察（待复测登记）**：T05 演练早期以选举超时 (150,300)ms /
心跳 25ms 运行时，debug 构建 + 每批 fdatasync 下观察到
`got:{self}` 形态失败，放宽至 (300,600)ms / 50ms 后演练 6+ 连绿。
当时未留存演练工件（铁律 10 缺口），观察值按「待 T07 复测登记」处理，
不作为验收证据。

**运营口径（两个独立旋钮）**：
1. `heartbeat_interval` ≥ 单次日志 fdatasync p99（直接决定读确认 ttl，
   是消除 `got:{self}` 的主旋钮）；
2. 选举超时下界 ≥ 数倍心跳间隔（防误选）。
T07 基准环境（release + 磁盘口径）按此登记。

## 4. WP01 §4/§5 单写者裁定的重审（显式）

WP01 §4 裁定「v0.1 单写者串行（进程内 `&self` 独占）；并发写冲突语义
留 WP02 复制层定义」。WP02 后的形态：

- **串行化主体从「进程」改为「raft leader + log 序」**：写不再依赖
  `&self` 独占，而是 leader 单点串行 append + 全组按 log 序 apply。
  投影同序重放的目的由裁定 7 保持——entry 行与 children 行是同组同一
  log 的两个状态机 section，apply 逐条按 log 序重放，「行先投影后」
  顺序与 WP01 单机一致。
- **「最后写者」语义的收紧**：v0.1 基线（代码注释 lib.rs「同槽异主属
  调用方违约，投影以最后写者为准」——注意该口径出自代码注释而非 WP01
  规格条文；其「最后」按进程内到达序）在复制层升级为**「按 log 序的
  最后写者」**：并发客户端写同一 leader 按 openraft 到达序入 log，
  apply 按 log 序 upsert。语义收紧而非放宽：投影陈旧窗口从「崩溃间隙」
  缩小为「复制延迟」。
- **结论**：WP01 §4/§5 单写者裁定**被复制层取代而非违反**。

## 5. 故障切换承诺

- **已 ACK 写入不丢**（关门 KPI）：ACK 前置条件 = 条目已 commit
  （quorum 持久化；fjall 日志批 fdatasync——持久化证据 =
  `t03_journal_durability_survives_unclean_close`：子进程
  `process::exit(9)` **立即退出不跑析构形态**（对持久性与 SIGKILL
  等价——协议写均先行 fdatasync）。leader 死亡后新 leader 必然从含
  该条目的 log 继续，apply 后可读（T05 failover 演练读回链闭合）。
- **ACK 前崩溃** = 客户端未收到应答，条目可能 commit 但未 apply、可能
  已 commit 未复制满、也可能根本未入 log——客户端超时语义（与 WP01
  v0.1 无事务口径一致）：视为未定；在请求 id 幂等机制（WP03）落地前，
  重试以同键 upsert 收敛（§3.1）。
- **演练形态**（T05 `t05_failover_under_10s_no_ack_loss`）：leader core
  停止（无优雅交接）→ 幸存者选举 → 新 leader 上全部 ACK 写入可读，
  实测 <10s（debug 构建口径；release 口径归 T07 报告）。
- **转移**：0.9.25 无显式 transfer API（进场核实）；演练形态 = 旧
  leader 停选举 + 目标节点 `trigger().elect()`（更高 term 迫使其让位），
  实测 <5s。运营级主动转移归 WP03+（需 leader 主动迁自动作）。

## 6. 分裂×复制耦合崩溃矩阵（裁定 6）

**目标态**（SPEC 裁定 6）：split 仅 leader 执行；搬移原子批作为源组
raft 日志条目复制；新分区组以空日志 bootstrap，初始数据由控制面在源组
日志覆盖搬移后按序写入新组日志；分裂期间路由由组注册表驱动双读合并
视图（WP01 §3 语义不变）。

**实现状态（诚实标注）**：T02 keyspace 收敛后单机分裂已元数据-only
（`split_partition` = splitting 分区行批 + active 批）；「分裂批经 raft
日志复制」与「新组 bootstrap」**尚未接线**——replica 层当前不触发
split。M1/M2 的「已测」均为 **WP01 单写者直连形态**（Hub::open 直连
fjall，不经任何 raft 组）；「单节点组拓扑」（members={self} 的 Replica
承载 WP01 行为）回归**未执行**，随 Hub 接线落地。

崩溃矩阵（列：阶段 × 注入点 × 不变量 × 恢复动作 × 状态）：

| # | 阶段 | 注入点 | 不变量 | 恢复 | 状态 |
|---|---|---|---|---|---|
| M1 | 源组 splitting 行批提交后 | WP01 `PT_META_COMMITTED` | 收尾批提交前：新分区行存在则必为 splitting（恢复方向确定）；键集不变 | open 重放收尾（幂等置 active） | 已测（单写者直连形态；组拓扑回归未执行） |

| M3 | 源组分裂批复制中 kill leader | 组生命周期点（新增） | follower 不触发分裂；log 无分裂半态 | 重选后新 leader 按日志收尾 | 规格态（待复制接线） |
