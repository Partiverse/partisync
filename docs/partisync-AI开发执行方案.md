# PartiSync AI 开发执行方案
## —— 可审计、分阶段交付的 AI 辅助开发作业体系

> 版本：v1.0 · 日期：2026-09-18
> 上游文档：[partisync-调研与构建方案.md](partisync-调研与构建方案.md)（技术选型与架构，下称「调研方案」）
> 读者：项目负责人、工程负责人、评审人、安全审计、未来的审计者
> 本文档回答三个问题：**① 用 AI 怎么把 PartiSync 造出来（工作流）；② 怎么证明造得对（可审计性）；③ 每个阶段交付什么、怎么验收（阶段计划）。**

## 0. 执行摘要

**核心理念：规格与测试是资产，实现是可再生的。**

AI 时代的工程审计对象发生迁移：AI 可以随时依据规格重新生成实现，因此**真正需要人负责、需要留档、需要评审的是规格（SPEC/ADR）、测试（含属性测试与基准）和评审记录**；实现代码退化为「规格的编译产物之一」。整套作业体系围绕这一点设计。

四条主线：

1. **治理**：十条铁律 + 人机分工 RACI 矩阵。人独占架构决策、密码学、安全边界与放行权；AI 负责实现、测试、文档与首轮对抗审查（§1）。
2. **可审计性**：一条从 RFC → ADR → SPEC → 任务 → PR → 提交 → CI 工件 → 里程碑报告 → 签名发布的**全链追溯 ID 体系**，配自动化追溯脚本；每个里程碑产出固定审计工件清单，缺件即未完成（§2、§7）。
3. **作业流程（SOP）**：SPEC→分解→测试规格→实现→验证→双通道评审→合入 的标准循环，含五道门禁 G0–G4；任务原子化（≤400 行 diff），每任务独立 AI 会话（§3）。
4. **质量体系**：七层测试金字塔（单测/属性/互操作/集成/模糊/混沌/基准）+ 变异测试抽检防「AI 写假测试」+ 基准回归门禁（§4–§5）。

**交付节奏与总时间线**（1 名架构负责人 + 1 名高级评审 + 0.5 安全，AI 全程辅助）：

| 阶段 | 内容 | 工期 | 累计 | 对外交付物 |
|---|---|---|---|---|
| **M-1** | 工程基建 + 审计演练 | 2 周 | 2 周 | CI 全门禁绿的仓库 + 追溯链 + 一次完整审计演练 |
| **M0** | 本地引擎（索引/CAS/CLI） | 4–6 周 | 7 周 | `partisync` CLI：百万文件索引、去重报告 |
| **M1** | 协议广度 + 网关 | 6–8 周 | 14 周 | S3/WebDAV/FTP 消费 + serve；rclone 互操作认证 |
| **M2** | 同步引擎 + 多端 + E2EE | 8–10 周 | 23 周 | 三设备同步、断网收敛、加密空间 |
| **M3** | Hub 集群 | 8–10 周 | 32 周 | 10⁹ 条目分片元数据、对账、分层 GC |
| **M4** | AI 层 | 6–8 周 | 39 周（≈9 个月） | 混合检索、MCP 工具面、数据集出口 |
| **M5** | 万亿路径（探索） | 滚动 | — | 联邦协议、10¹² 仿真报告 |
| **M6** | 产品化 | 滚动 | — | Tauri 壳、扩展系统 |

预算量级：M-1 至 M4 约 **550–650 个原子任务、8–15 亿 token、$2k–$25k API 成本**（模型单价 $1–15/M 混合计价，含 ×1.5 重试系数，见 §8）。

## 1. 治理总纲：AI 辅助开发的原则

### 1.1 十条铁律

| # | 铁律 | 执行机制 |
|---|---|---|
| 1 | **规格先行**：没有通过评审的 SPEC，AI 不写一行实现 | G0 门禁；commit 钩子校验任务挂接已批准 SPEC |
| 2 | **追溯唯一**：一切提交必须挂任务 ID | commit-msg 钩子 + CI 校验；无 ID 分支不可开 PR |
| 3 | **原子交付**：单 PR ≤400 行 diff（锁文件/生成物除外） | CI 的 PR 大小检查；超限自动要求拆分 |
| 4 | **测试即规格**：行为契约先于实现，测试规格人审 | G1 门禁；属性测试清单（§4.2）为强制项 |
| 5 | **门禁前置**：CI 红灯禁止合入，覆盖率只升不降 | 分支保护 + 覆盖率差值检查 |
| 6 | **双通道审查**：AI 对抗审查报告 + 人工终审，两者留档 | PR 模板强制附 AI 审查报告；报告入 `docs/reviews/` |
| 7 | **地基人工**：schema 迁移、密码学、安全边界、公共 API 由人设计并双倍评审 | 钉子清单（§1.3）；此类 PR 需两名人类评审 |
| 8 | **无聊依赖**：新增依赖必须过 cargo deny + ADR 记录理由 | CI 依赖差量检查；deny.toml 白名单制 |
| 9 | **会话即弃**：每任务独立 AI 会话，禁止「顺手」跨任务修改 | PR diff 范围与任务声明的文件清单比对（CI 软检查+评审硬检查） |
| 10 | **审计即工件**：里程碑不出产规定审计工件 = 未完成 | G3 门禁检查单（§7.1） |

### 1.2 人机分工 RACI 矩阵

R=AI 起草/实现 · A=人最终负责 · C=被咨询 · I=知会。（A 不可授予 AI。）

| 活动 | AI | 人类 | 产物 |
|---|---|---|---|
| RFC / 架构决策 | 起草备选方案、收集论据 | **独占终审与拍板** | RFC/ADR 文档 |
| SPEC 编写 | 起草任务规格 | 评审批准（G0） | `docs/specs/*.md` |
| 任务分解 | 建议分解 + 依赖图 | 批准 | 任务卡（issue） |
| 测试规格 / 属性测试 | 编写 | 评审（G1） | 测试代码 + 属性清单 |
| 业务逻辑实现 | **主力** | 抽审 30–100%（按风险分级） | 实现 PR |
| 密码学与安全边界 | 解释背景、写文档 | **独占设计与实现评审** | 双人评审 PR |
| 代码评审（第一轮） | **对抗审查**（找 bug/安全/规格违背） | — | AI 审查报告 |
| 代码评审（终审） | — | 每个必 PR | Review 记录 |
| 基准 / 性能调优 | 跑基准、分析报告、提出补丁 | 认可结论 | 基准报告 |
| 文档 / 发布说明 | 主力起草 | 终审 | docs/changelog |
| 依赖升级 / 重构 | 独占执行（低风险类） | 事后抽检 10% | 升级 PR |
| 里程碑放行（G3） | 汇总数据生成报告草稿 | **独占** | 里程碑报告 |
| 外部安全审计配合 | 整理 unsafe 清单/攻击面 | 主谈 | 审计报告 |

### 1.3 AI 能力边界与风险分级

**交给 AI 高效完成的**：有明确输入输出契约的模块实现、测试生成（含属性测试）、样板/脚手架、文档、依赖机械升级、基准脚本、日志与错误信息补全、首轮代码审查。

**必须人主导（钉子清单，双人评审）**：
- SQLite schema 与迁移文件（数据是资产，迁移错误不可逆）；
- 一切 `unsafe` 块、FFI 边界（fuser/io-uring/ort）；
- 密码学：密钥层次、AEAD 用法、KDF 参数、配对协议（§5.3）；
- Provider SPI 公共 trait 与 MCP 工具面（对外契约，改起来贵）；
- 权限/授权模型与网关鉴权。

**明确禁止 AI 独断的**：新增顶层依赖、修改 CI 门禁阈值、删除测试或放宽断言、变更 deny.toml 白名单、任何「让测试变绿」而非「让行为正确」的修改（评审重点盯这条）。

## 2. 可审计性体系

> 设计目标：一名**此前完全未参与**的审计者，仅凭仓库内工件，能在一天内重建任意一次变更的「为什么做、要求什么、做了什么、如何证明、谁做的、谁批的」。

### 2.1 追溯链与编号体系

```
RFC (docs/rfcs/NNNN-*.md)                为什么：问题与方案论证
  └─ ADR (docs/adr/NNNN-*.md)            决策：选定方案与后果（不可变，只增不改）
      └─ SPEC (docs/specs/<Milestone>-WP<n>.md)   要求：工作包级验收规格
          └─ TASK (issue #n, 卡片含合同)           任务：原子工作单元
              └─ BRANCH m<m>/wp<n>-t<n>-<slug>
                  └─ PR (链接任务+SPEC；附 AI 审查报告)
                      └─ COMMITS (trailer: Task-ID / AI-Assist / Reviewed-By)
                          └─ CI RUN (工件：测试报告/覆盖率/基准/模糊/扫描)
                              └─ MILESTONE REPORT (docs/reports/<M>-report.md)
                                  └─ RELEASE (签名 tag + SBOM + 变更日志)
```

**编号规则**：`M{阶段}-WP{工作包两位}-T{任务两位}`，如 `M0-WP03-T01`。阶段号 M-1 记作 `M-1`。编号永不复用；取消的任务标 `wontfix` 留痕。

**提交规范**：
```
<type>(<scope>): <subject> [M0-WP03-T01]

Task-ID: M0-WP03-T01
Spec: docs/specs/M0-WP03.md
AI-Assist: <agent/model>@<version> (implementation+tests)
Reviewed-By: <human-id> (final)
```
type 用 conventional commits（feat/fix/test/docs/refactor/chore）；`AI-Assist` 披露 AI 参与类型；纯人工提交可省略 AI-Assist 但不得虚报。

**自动化追溯工具（xtask 子命令，M-1 交付）**：
- `cargo xtask trace M0-WP03`：打印该工作包全链（SPEC→任务→PR→提交→CI 工件→覆盖的测试）；
- `cargo xtask report M0`：汇总里程碑统计并生成报告骨架；
- commit-msg 钩子：无 `Task-ID` 拒收；PR 校验 job：PR 内所有提交的 Task-ID 一致且属于已批准 SPEC。

### 2.2 每里程碑强制审计工件清单

| 工件 | 产生方式 | 存放 |
|---|---|---|
| 里程碑报告（模板 §附录 D） | `xtask report` 生成 + 人填充结论 | `docs/reports/` |
| 测试证据 | CI 工件（测试报告+覆盖率快照）链接进报告 | CI 保留 90 天+关键 run 固化 |
| 基准报告（与上一阶段基线对比表） | bench job 产物 | `docs/reports/bench/` |
| 模糊测试运行证据（累计时长、崩溃数、修复链接） | fuzz job 汇总 | 同上 |
| 变异测试抽检报告（核心 crate） | cargo-mutants job | 同上 |
| 安全扫描（cargo audit / deny / unsafe 清单增量） | CI 汇总 | 同上 |
| 本阶段 ADR 全集 | 评审通过的 ADR | `docs/adr/` |
| AI 使用披露统计（AI 辅助任务占比、AI/人审查发现数） | `xtask report` 从 trailer 统计 | 报告内 |
| 遗留问题与债务登记 | 人填写 | 报告内 |

### 2.3 度量仪表盘（周更，自动采集）

- **交付**：PR 中位周期、PR 大小分布（P50/P90 行数）、回滚/回退率；
- **质量**：覆盖率趋势、变异分数趋势、基准关键指标趋势、模糊崩溃累计、互操作矩阵通过率；
- **AI 治理**：AI 辅助任务占比、AI 审查发现被采纳率、人工评审否决率（否决率骤升 = 规格质量恶化信号）。

## 3. AI 开发标准作业流程（SOP）

### 3.1 交付循环与五道门禁

```
┌─ G0 ──────┐   ┌─ G1 ──────┐          ┌─ G2 ──────┐
│ SPEC 批准  │→ │ 测试规格批准 │→ 实现 →验证→│ PR 合入   │ → 集成/混沌/互操作 夜间套件
└───────────┘   └───────────┘   (AI)  (CI) └───────────┘        │
                                                             ┌─ G3 里程碑门 ─┐
                                                             │ 报告+放行签字 │
                                                             └──────┬───────┘
                                                                ┌─ G4 发布门 ─┐
                                                                │ 签名+SBOM   │
                                                                └────────────┘
```

**步骤细则**（每任务执行，编号 S1–S8）：

- **S1 规格（G0）**：人+AI 起草工作包 SPEC（模板 §附录 A）。必含：动机、输入输出契约（类型签名/错误语义）、验收标准（可执行）、非目标、涉及文件清单、风险。人批准后 SPEC 冻结（修改需新版本号并留 changelog）。
- **S2 分解**：AI 把 SPEC 分解为任务卡（每卡 ≤1 人日等价工作量、单一职责、可独立验证、依赖显式），人批准入板。
- **S3 测试规格（G1）**：AI 依 SPEC 先写测试：单测骨架 + 属性测试（引用 §4.2 不变量清单）+ 夹具。人只审测试（此时实现不存在，测试即规格的精确化）。批准后测试合入 `main`（此时 `#[ignore]` 或空实现桩使其编译通过）。
- **S4 实现**：AI 在**独立会话**中实现。上下文 = AGENTS.md + 该任务 SPEC + 相关 crate 的局部 AGENTS.md + S3 的测试。禁止改动任务文件清单之外的内容。实现循环：编译 → clippy → 本地测试 → 自查报告（AI 列出与 SPEC 的逐条对照）。
- **S5 验证（CI）**：PR 触发全门禁：fmt / clippy `-D warnings` / test / 覆盖率差值（触及文件不得下降 >1pp）/ 基准差值（关键路径回退 >10% 阻断）/ cargo deny / cargo audit / 模糊冒烟（60s）/ 变异抽检（核心 crate 每 10 个 PR 抽 1 个）。
- **S6 双通道审查（G2）**：① **AI 对抗审查**：独立会话，角色为「找茬者」，输入 SPEC+diff，输出结构化报告（见 §附录 E-P2），发现的缺陷必须修复或以理由驳回；② **人工终审**：核对 AI 报告处理情况、抽查关键路径、确认无「为绿而绿」。钉子清单类 PR 需第二名人评审。
- **S7 合入**：squash merge 保留 trailers；任务卡关闭；度量入账。
- **S8 集成**：`main` 每夜跑集成/混沌/互操作套件（§4.4–4.7）；红灯按 §3.6 处理。

### 3.2 上下文工程

- **仓库根 AGENTS.md**：编码规范、crate 地图与依赖方向、常用命令、禁止事项（禁止引入新顶层依赖、禁止改门禁、禁止删测试、禁止从记忆写 API——必须查证 crate 文档）。
- **每 crate 局部 AGENTS.md**：该 crate 的契约、不变量、已知坑（随 PR 维护）。
- **会话纪律**：一任务一会话；会话开头注入 SPEC 而非依赖对话记忆；长任务拆卡而不是长会话。
- **规格即提示词**：提示词模式库（§附录 E）与模板绑定，避免即兴提示。

### 3.3 任务粒度标准

合格任务卡：单一职责；≤400 行 diff 预估；明确的契约（输入/输出/错误）；明确的验证方式（测试/基准/脚本）；文件清单 ≤8 个；依赖的其他任务 ID 显式列出。超出即拆分。**典型任务尺寸：2–6 小时人等效工作量。**

### 3.4 风险分级与评审深度

| 级别 | 定义 | 人工终审深度 |
|---|---|---|
| R0 低 | 纯内部、有测试覆盖、无 IO/unsafe/协议 | 抽审 30%，AI 审查报告必附 |
| R1 中 | 跨 crate、IO 密集、性能敏感 | 全审 diff |
| R2 高 | 钉子清单（schema/unsafe/crypto/API/鉴权） | 双人全审 + 逐行对照 SPEC |

### 3.5 失败处理与回滚

- CI 红灯：任务回炉（S4 重入），禁止在 PR 中放宽测试——放宽断言本身需独立 PR+理由；
- 夜间套件红灯：当日定位归因（bisect 自动化），修复任务优先级置顶；连续两晚红灯 → 冻结 `main` 新合入直至修复；
- 里程碑门禁未过：不允许「带病放行」；要么补齐，要么正式降级范围并在报告中登记；
- 回滚：单 PR 回滚（revert 保留原 trailers + 新 Task-ID），禁止 force-push `main`。

## 4. 质量保障体系

### 4.1 测试金字塔（七层）

| 层 | 内容 | 触发 | 责任 |
|---|---|---|---|
| 1 单元 | 纯函数/类型/解析器 | 每 PR | AI 写，人审 |
| 2 **属性**（核心） | 数学不变量的 proptest | 每 PR | 清单见 §4.2，人审规格 |
| 3 集成 | 真 S3（rustfs/MinIO 容器）、WebDAV/FTP 夹具、SQLite/redb 真库 | 每 PR（冒烟）+ 每夜（全量） | AI 写夹具 |
| 4 互操作 | rclone/标准客户端 对打 | 每夜 + 里程碑 | 见 §4.7 |
| 5 模糊 | 协议解析、CDC、URI | 每夜累计 + 里程碑长跑 | 见 §4.3 |
| 6 混沌/崩溃一致性 | failpoint 注入、断网、进程杀 | 每夜 | 见 §4.4 |
| 7 基准 | criterion 套件 + 回归门禁 | 每 PR（关键路径）+ 每夜（全量） | 见 §4.5 |

### 4.2 属性测试强制清单（同步/分布式系统的「可执行数学」）

| # | 模块 | 不变量 | 测试形态 |
|---|---|---|---|
| P1 | CDC 分块 | 同输入 → 逐位相同的分块序列（确定性） | proptest 任意字节流 |
| P2 | CDC 分块 | 在位置 p 插入字节后，p 之后某距离外的边界不受扰动（内容定义性） | proptest + 边界距离断言 |
| P3 | CDC 分块 | 块长 ∈ [min,max]，均值落在目标带宽内 | 统计断言 |
| P4 | CAS | `hash(content) == root(chunks)`；同内容二次入库 → 引用计数 +1、不新增块 | 模型对照测试 |
| P5 | HLC/oplog | 时间戳严格单调；同物理时间并发可全序 | 并发线程模型测试 |
| P6 | **收敛性** | 任意两副本应用**同一操作集**（任意顺序、含重复）后状态等价 | 线性化模型测试（核心，M2 起） |
| P7 | Merkle 对账 | 无假阴性（树根相等 ⇒ 无漏检差异，概率界内）；分歧区间必被下钻覆盖 | 随机差分注入 |
| P8 | 崩溃日志 | 任意时点崩溃 → 重放后达一致状态且不丢已确认操作 | failpoint 枚举（§4.4） |
| P9 | Provider caps | 声明无校验和能力的后端，绝不走校验和比较路径 | caps ↔ 行为一致性测试 |
| P10 | 路径映射 | Unicode/非法字符在每 provider 编码方案下 round-trip 无损 | 表驱动 + 随机 Unicode |
| P11 | 冲突策略 | 同名双改 → 两者皆可寻址（保留两者语义），血缘可查 | 模型测试 |
| P12 | 传输 | 任意丢块/乱序/重传 → 接收端重组后 BLAKE3 必验；验败必拒 | 注入测试 |

### 4.3 模糊测试目标

`cargo-fuzz` 目标：S3 响应 XML/错误解析、WebDAV PROPFIND 多状态解析、FTP 控制通道命令解析、自有块交换协议（BEP 类）帧解码、CDC 对抗输入（边界粘滞）、URI 解析、pack 索引解析。节奏：每夜每目标 ≥1h 累计；里程碑门禁前每目标 ≥24h 长跑，崩溃清零（发现→修复→回归用例入库）。

### 4.4 混沌与崩溃一致性（同步引擎的生死线）

- **failpoint 框架**：在写日志/写库/写块/发消息前后注入崩溃点；测试枚举每个 failpoint：杀进程→重启→断言 P8 不变量；
- **网络混沌**：docker 网络分区/延迟/丢包（tc）下的三节点收敛测试；设备离线 24h 后重连收敛；
- **磁盘故障**：pack 损坏位翻转 → EC 修复路径验证（M3）；
- **时钟混乱**：系统时钟回拨/跳跃下 HLC 行为（P5 扩展）。

### 4.5 基准回归门禁

criterion 套件 + 仓库内基线（`docs/reports/bench/baseline.json`）。**门禁指标**（PR 级阻断，>10% 回退需 ADR 豁免）：
- 扫描吞吐（files/s）、索引写放大；
- LIST p99（合成 10⁷ 条目库）；
- 传输吞吐（MB/s，本地回环 + tc 模拟 100ms/1% 丢包）；
- 同步收敛时间（固定差异集）；
- 块交换协议每块开销（µs）。

里程碑级验收基准沿用调研方案 §7 KPI 表（如 M0：笔记本 10⁶ 文件索引 <10min；M3：10⁹ 条目导入 <24h/10 节点）。

### 4.6 变异测试抽检（防「AI 假测试」）

AI 生成的测试可能「看起来覆盖、实则不断言」。对策：`cargo-mutants` 对核心 crate（cas/cdc/graph/sync/transfer）每 10 个 PR 抽 1 个跑变异；里程碑门禁跑全量。**分数门槛：核心 crate ≥60%（M0）→ ≥70%（M2+）**。分数骤降即测试质量恶化报警。

### 4.7 互操作认证矩阵

| 对端 | 场景 | 阶段 |
|---|---|---|
| **rclone** | 把 partisync S3 端点配置为 remote：copy/ls/check/bisync | M1 起每夜 |
| rclone WebDAV 客户端 | serve webdav 读写 | M1 |
| FileZilla / curl | serve ftp / sftp(若启用) | M1 |
| Windows WebDAV 客户端 / Cyberduck | serve webdav 真实客户端行为 | M1 里程碑 |
| Linux `mount` + fuser | FUSE 挂载：随机读/顺序写/写回日志 | M1(只读)→M2 |
| aws-cli | 对 partisync S3：MPU、预签名、ListV2 游标 | M1 里程碑 |
| MCP 参考客户端 | MCP 工具调用全场景 | M4 |

互操作失败 = 发布阻断级缺陷（语义诚实原则，见调研方案 §5.13）。

## 5. 供应链与安全

### 5.1 依赖治理

- `Cargo.lock` 提交；新顶层依赖需 ADR + cargo deny 通过（许可证白名单：Apache-2.0/MIT/BSD/ISC/Unicode-3.0/MPL-2.0；刻意排除需说明）；
- 每夜 `cargo audit` + Dependabot/renovate（AI 执行升级 PR，人抽检 10%）；
- 禁用清单直接写进根 AGENTS.md：**sled（停更）、instant-distance（停更）**，见调研方案 §6。

### 5.2 unsafe 政策

- 默认零 unsafe；确需（io_uring、FUSE、ort 回调）：PR 标 R2、双人评审、注释写明安全论证与不变量；
- `xtask unsafe-inventory`：里程碑报告自动附 unsafe 行数增量清单。

### 5.3 密码学审查（M2 前外部审计，G3 组成部分）

范围：密钥层次（根→空间→文件/块派生）、XChaCha20-Poly1305 用法、配对协议（助记词+挑战签名+会话密钥）、预签名 URL 过期与作用域。要求：只用 audited 原语组合，**不自造密码学**；审计报告入 `docs/reports/security/`。M4 追加 MCP 面与网关鉴权的外部渗透测试。

### 5.4 发布工程

- 可复现构建（`cargo build --locked` + 固定 toolchain 由 rust-toolchain.toml 钉住）；
- `cargo auditable` 嵌入依赖清单 → SBOM；发布产物签名（minisign/工程签名密钥，密钥双人保管）；
- 变更日志由 AI 从 PR 集自动起草、人终审。

## 7. 里程碑门禁评审协议（审计如何执行）

### 7.1 G3 检查单（自动 + 人工两部分）

**自动部分（脚本判定，输出进报告）**：

5. cargo audit/deny 干净；unsafe 清单增量已审；
6. 互操作矩阵全绿；
7. 混沌/夜间套件最近 7 天无未分类红灯。

**人工部分（签字）**：
8. 本阶段 ADR 完整覆盖已做决策；债务登记现实；

11. AI 使用披露统计合理，无「AI 独断钉子清单项」记录。

**放行**：架构负责人 + 评审人双签（M2/M4 加安全负责人三签）。报告归档 `docs/reports/`，任何豁免须 ADR 记录。

|---|---|
| S1–S3（规格起草+分解+测试规格，AI 参与） | ~0.3M |
| S4 实现（含编译修复循环、自查） | ~0.6M |
| S6 AI 对抗审查 | ~0.2M |
| S7–S8 修补/文档/杂项 | ~0.2M |
| 夜间/门禁 agent 与报告生成摊销 | ~0.2M |
| **合计** | **~1.5M token/任务** |

**总量**：650 × 1.5M ≈ **10 亿 token**（±50%）。按混合单价 $1–15/M token：**$1k–$15k**；取上界加冗余 → 预算口径 **$2k–$25k**。CI（自托管 runner 为主）与测试床硬件（1 台 Mac + 3 台 Linux 小主机/云主机）另计。

**人力**：1 名架构负责人（SPEC/ADR/放行，~100%）+ 1 名高级评审（终审/混沌床，~100%）+ 安全顾问（0.5，M2/M4 峰值）。三人加 AI 可把 M-1→M4 压缩至 ~7 个月；两人配置 ~9–10 个月。

## 9. 风险登记册（AI 开发特有风险）

| # | 风险 | 信号 | 缓解 |
|---|---|---|---|
| R1 | AI 幻觉 API/字段 | 编译错、运行 panic | 编译门禁；AGENTS.md 强制「查证再写」；依赖钉版 |
| R2 | **假测试**（覆盖而不断言） | 覆盖率高但变异分数低 | 变异测试抽检（§4.6）+ G1 人审测试规格 |
| R3 | 架构腐蚀（跨层依赖、上帝模块） | 依赖方向违规、crate 膨胀 | fitness function：CI 依赖方向检查（cargo modules/自写脚本）+ 公共 API 变更需 ADR |
| R4 | 规格质量漂移（AI 起草敷衍） | 人工否决率上升 | 仪表盘监控否决率；规格模板强制验收标准可执行 |
| R5 | 「为绿而绿」（放宽测试求合入） | 断言删改 diff | 放宽断言需独立 PR；评审重点项；夜间黄金集 |
| R6 | 会话上下文污染（跨任务私货） | diff 超出文件清单 | CI 软检查 + S6 硬检查 |
| R7 | 许可证污染（AI 复制 Copyleft 片段） | deny 报警 | cargo deny；AGENTS.md 禁止逐字复制；抽查 grep |
| R8 | 模型行为漂移/弃用 | 质量波动 | 每里程碑钉模型版本记录于报告；规格+测试在手，实现可再生成（本方案的兜底哲学） |
| R9 | 评审瓶颈（人成为流水线堵点） | PR 周期中位数上升 | R0 级 30% 抽审；AI 预审分流；必要时增评审人 |
| R10 | token 预算失控 | 周消耗偏离模型 >2σ | 任务粒度上限；仪表盘预算告警；废弃会话早止损 |
| R11 | 关键人风险 | 单点评审/签发 | ADR/SPEC 文化使知识外化；放行角色可移交（两周交接期写进流程） |

## 附录 E：提示词模式库（角色模板）

```
P1 实现者:
  你是实现代理。上下文=AGENTS.md+SPEC{file}+测试{files}。只改文件清单内文件。

  你是找茬评审。输入=SPEC+diff。只找问题: 与 SPEC 偏差/边界条件/错误处理缺失/
  并发与 IO 风险/安全/测试是否真断言。输出: 结构化清单(严重度/位置/理由/建议)。
  不许夸奖。没有发现也要写"未发现"并说明检查了什么。

P3 测试员(G1):
  依据 SPEC 生成属性测试+单测骨架。属性必须引用不变量清单编号(P1–P12)。
  先写测试后写实现;测试合入时以桩实现通过编译。

P4 分解者(S2):
  输入=批准 SPEC。输出=任务卡列表(编号/契约/验证方式/文件清单/依赖图)。
  每卡 ≤1 人日等价;超过即拆。

P5 重构者:
  输入=重构目标+不变量清单+现有测试。约束: 行为不变(测试全绿+基准差值内)。
  输出=分步小 PR 序列。
```
