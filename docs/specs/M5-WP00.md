## 3. WP01 草案：UploadAck 协议设计

### 3.1 现状（M4-WP04 §2 协议发现）

`crates/partisync-hub/src/iroh_channel.rs:171-174`：

> iroh-blobs 0.103 的 push 是 **fire-and-forget**（设备 `send.finish()` 即返回，不读 hub 应答），
> 若设备 push 后立即关连接，hub 可能还没 accept 该流，数据随连接丢弃。
> 因此设备侧必须保持连接直到 hub 同步完成（**协议层的 UploadAck，M5 设备侧执行器落地**）。

### 3.2 协议契约（草案）

#### 3.2.1 帧格式

```
[1B version=0x01][1B type][4B length][payload...]

type 字段：
  0x01  UploadReq   (设备 → hub)   payload: { content_id: u64, size: u64, hash: blake3-32 }
  0x02  UploadAck   (hub → 设备)   payload: { content_id: u64, status: u8, error_msg: string }
  0x03  UploadNack  (hub → 设备)   payload: { content_id: u64, reason: string }

status 字段：
  0 = Accepted  (CAS 写入 + refcount+1 完成)
  1 = Duplicate (已存在，跳过 refcount)
  2 = Rejected  (hash 不匹配 / 配额超限等)
  3 = Retrying  (hub 临时故障，设备按 backoff 重传)
```

#### 3.2.2 时序

```
设备                                              hub
  │                                                 │
  │─── Stream: chunk[X..Y] ──────────────────────►  │
  │                                                 │
  │  (send.finish())                               │
  │                                                 │
  │  ◄──── ack receipt（stream-level）──────────────│  (iroh-blobs)
  │                                                 │
  │                                                 │
  │  (设备轮询等待 hub 应答)                       │
  │                                                 │
  │  ◄──── UploadAck{status=Accepted} ────────────│  ← 协议层
  │                                                 │
  │  (设备关闭连接)                                │
```

**关键不变量**：设备收到 UploadAck 后才能关闭连接，否则数据可能在 hub 端未落库。

#### 3.2.3 超时与重试

- 设备默认超时：30s（可配置 `--upload-ack-timeout`）
- 重试策略：指数 backoff（1s → 2s → 4s → 8s，上限 5 次）
- 重试上限后放弃 → 用户层告警 + 离线队列待复传

### 3.3 实现要点

1. **Hub 端**（`crates/partisync-hub/src/iroh_channel.rs`）：
   - 在 `handle_incoming` 末尾，CAS 写入成功后立即发 `UploadAck` 帧
   - 失败回 `UploadNack`（hash mismatch / disk full / quota exceeded）
   - **不阻塞** iroh-blobs 内部流（ack 帧走独立 QUIC stream 子协议）

2. **设备端**（新建 `crates/partisync-sync/src/upload_acker.rs`）：
   - 在 push 完成后维护「待 ack 列表」（按 content_id）
   - 收到 ack 后从列表移除 + 触发上层回调（"上传完成"事件）
   - 超时由 tokio::time::timeout 实现 + backoff

3. **协议协商**：
   - 设备 hello 帧声明支持的 protocol version（`version=0x01`）
   - hub 检查 version 兼容性 → 不匹配则拒绝（错误码 `PROTOCOL_VERSION_MISMATCH`）

### 3.4 测试要求

- `crates/partisync-hub/tests/wp01.rs` 新增：
  - `upload_ack_basic`：正常 push + 收到 ack + 关闭连接
  - `upload_ack_duplicate`：hub CAS 已存在 → status=1（Duplicate）ack
  - `upload_ack_rejected`：hash mismatch → status=2 (Rejected) ack
  - `upload_ack_timeout`：设备 30s 未收到 ack → 重试
  - `upload_ack_version_mismatch`：设备版本 0x02 / hub 仅支持 0x01 → 拒绝
- 集成测试套件（loopback offline）端到端验证「push → ack → close → 设备端 CAS 检查」
- 混沌：kill -9 设备端在 push 后 / ack 前 → hub 不能 lost data

### 3.5 不在范围

- 多 hub 联邦（WP02）
- 真实 WAN 测试（仅 loopback）
- 重传加密（ack 帧明文，pfs 由 ECDH 配对层保证）
