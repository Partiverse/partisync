# SPEC: M5-WP02 —— 联邦路由协议：多 Hub 按 space 路由、反熵视图同步与 Raft 视图

版本: 0.1 · **状态: 批准（依用户 2026-09-24「继续 M5-WP02」指令 + M5「按顺序执行」
既定授权，按 M3-WP02 先例视同批准）** · 关联: 执行方案 §6.6、调研方案 §4.1
（万万亿 = 联邦聚合）、M5-WP00 §1 工作包图、M3-WP02（openraft 每分片一组 +
注册表组 pid=0）· 上游: M5-WP01 UploadAck（iroh 通道不动）、M3-WP03 注册表
（`registry.rs`）
负责人: @lead · 起草日期: 2026-09-24

## 动机

M3 交付单 hub 元数据平面（分片 + openraft 复制 + 注册表），M5-WP01 交付设备侧
可靠上传。当前一个部署只有一个 hub：空间数量与 hub 承载力绑死，与调研方案
§4.1「万亿 = 联邦聚合、单空间 10⁹–10¹¹」的定位矛盾。WP02 交付最小可用联邦：
**多个 hub 各自持有若干空间，任一 hub 可应答任意空间的路由查询；空间归属经
协商产生、经反熵同步收敛；路由视图经各 hub 自身 raft 组（group 0）复制**——
崩溃安全、线性一致读，且为 WP03（分布式扫描调度）提供「哪些空间在哪个 hub」
的调度底座。

## 裁定总览

1. **路由单元 = space_id，v0.1 不做 content_id 前缀分片**。M5-WP00 §1 表述
   「多 hub 按 space 路由」为准；路由行数量级 = 空间数（≤10⁴，注册表同口径），
   全量视图交换可行。content_id 前缀路由 + 0-RTT 归后续卡（本 spec 非目标）。
2. **路由视图 raft 化**（「Raft 视图同步」字面兑现）：路由行持久化于注册表组
   （pid=0）新业务节 `r-route` keyspace，经 `RegistryCmd::SetRoute` 入组 0
   日志——写崩溃安全（已 ACK 不丢，raft 承诺），读线性一致（复用
   `ensure_linearizable` + keyspace 直读，与 `RegistryService::space` 同构）。
   不另立联邦共识组：注册表组已是「全局元数据」的既定落点，v0.1 不新增
   raft 组拓扑。
3. **传输零新依赖**：hub↔hub 复用 M3-WP02 紧凑帧 `[len u32 BE][version u8]
   [payload]`，载荷 = serde_json `FedFrame` 信封（与 openraft `NetRequest`
   信封族区分，不共享枚举）。iroh 替换留位 = version 字节（裁定同 M3-WP02 §4）。
   联邦口 v0.1 无认证，与 raft RPC 口（M3 v0.1）同一安全姿态（局域网/专线
   假设）；mTLS / iroh 传输归后续卡（见风险）。
4. **合并规则全协议唯一**：路由行 `RouteRow{ space_id, hub_id, addr, epoch }`；
   逐 space 胜者 = epoch 更大者，同 epoch → hub_id 更小者。确定性——任两 hub
   对同一输入得出同一视图（反熵收敛的充要条件）。无删除：空间不可删（注册表
   现无 delete-space 命令），路由只增/转移（转移 = 更高 epoch 换 hub_id），
   故反熵无需墓碑。
5. **协商 = RouteClaim（定向单行合并）**：claimant 提案 `RouteClaim{space,
   claimant, addr, epoch=local_max+1}`；收件方以裁定 4 规则与本视图合并——
   提案胜出则接受并落本地 raft（`accepted=true`），否则回当前胜出行；claimant
   收 `accepted=true` 后落本地。并发 claim（同 epoch）由 tie-break 确定性收敛，
   败者经裁决应答即时改写。epoch 单调语义：每个空间每有一个新提案才 +1，
   同一 hub 重申同 epoch 是幂等 no-op（合并相等即跳过）。
6. **反熵 = 握手全量交换 + 周期重放**：`Hello{hub_id, addr}` →
   `HelloAck{hub_id, addr, routes=本地全量视图}`，双向各自 merge 落盘；
   周期间隔（默认 5s，可配）重放直至视图稳定。v0.1 无增量推送/订阅。
7. **设备面 v0.1 = redirect 门**：`HubService::route_for(space_id)` 读本地
   raft 视图 → `Local` / `Redirect{hub_id, addr}` / `Unknown`（触发联邦层
   resolve：本地 miss → 逐 peer `RouteQuery` → 全 miss 可 claim）。iroh 数据
   面不在本 WP 改动——设备侧行为（拿到 Redirect 后改推 home hub）归设备侧
   执行器后续卡；CAS 块随 home hub 放置是派生性质，不新增机制。
8. **Hub 身份静态配置**：`FedConfig{ hub_id: u64, addr: String,
   peers: BTreeMap<u64, String> }`，构造期注入；动态成员/选主归后续。
9. **分区语义诚实化**：网络分区期间陈旧视图可产生错误重定向——设备在目标
   hub 落到非本 hub 空间时得到下一跳 Redirect 或触发协商，收敛由反熵 +
   claim 收口（查询只答本地视图，不代查，天然防环；测试以双 hub loopback
   断言重 join 收敛）。跨 hub 无事务、无跨 hub 线性一致（M3-WP02 裁定 5
   「跨分片无事务」的联邦版），单空间内语义不降级。

## 契约

### 1. 数据模型（`r-route` keyspace，键 = space_id UTF-8）

| 项 | 形态 |
|---|---|
| `RouteRow` | `{ space_id: String, hub_id: u64, addr: String, epoch: u64 }`（serde_json 行） |
| `RegistryCmd::SetRoute` | 新命令变体：upsert 单行（SM apply 侧确定性） |
| `FederationView` | 只读面：`rows()`（全量）/ `route(space_id)`，线性一致确认后直读 keyspace（同 `RegistryService::space` 通道） |

### 2. 线协议（`FedFrame`，serde_json 信封）

```
请求（hub → hub）                应答
  Hello   { hub_id, addr }        HelloAck { hub_id, addr, routes: Vec<RouteRow> }
  RouteQuery { space_id }         RouteAnswer { route: Option<RouteRow> }
  RouteClaim { space_id, claimant, addr, epoch }
                                  ClaimVerdict { accepted: bool, winner: Option<RouteRow> }
```

- 帧层直接复用 [`crate::net::{read_frame, write_frame, FRAME_VERSION,
  MAX_FRAME_BYTES}`]；信封变体不匹配 = 连接重置（同 `TcpNetwork` 口径）。
- 长连接懒建、串行复用、错误重置（`FedClient`，`TcpNetwork` 同构但非
  openraft trait）。

### 3. 合并与协商语义

- `merge(local_row, incoming_row) -> Option<RouteRow>`：incoming 胜出才返回
  Some（写侧去重：与本地相等则 no-op）；胜出规则见裁定 4/5。
- 握手与 claim 的落盘路径同一条：胜出行经 `RegistryCmd::SetRoute` 入本 hub
  组 0 日志——两 hub 视图交换的收敛点各自经过 raft，崩溃中断后重启续收敛。
- `resolve_space(space_id)`（联邦层组合子）：本地视图命中 → 返回；miss →
  逐 peer（hub_id 升序）`RouteQuery`，首个命中返回；全 miss → `Unknown`
  （是否 claim 由调用方决定——redirect 门不 claim，显式接管入口才 claim）。

### 4. HubService 面（T06）

- `route_for(&self, space_id) -> Result<RouteDecision, ReplicaError>`，
  `RouteDecision::{Local, Redirect{hub_id, addr}, Unknown}`；
  `Unknown` 到 `Redirect/Local` 的升级由联邦层 `resolve_space` 完成
  （service 层保持纯本地视图，不持网络）。

## 验收标准（可执行，测试先行）

- [ ] **路由视图 raft 化**：`SetRoute` 经组 0 日志；`RegistryService` crash
      后重开路由行不丢（复用 wp03 crash 演练口径）；读经
      `ensure_linearizable`。
- [ ] **双 hub 全链**（loopback）：A claim space → 握手同步 → B 本地视图含
      该行；B `route_for` 返回 `Redirect(A.addr)`。
- [ ] **合并确定性**：并发 claim（A/B 同 space 同 epoch）→ 两端视图收敛到
      同一 winner（hub_id 小者）；重放相同交换不再变更视图（幂等）。
- [ ] **协商即时改写**：claim 败者收到 `ClaimVerdict{winner}` 后本地立即
      收敛，不等周期握手。
- [ ] **分区恢复**：断开 peer 期间本地视图照常应答；重连后一次握手收敛到
      两侧视图相等。
- [ ] **redirect 门**：`route_for` 三分支语义测试；`resolve_space` 全 miss
      → `Unknown`，peer 命中 → 正确行。
- [ ] **回归**：fmt/clippy/test 全绿；M3-WP01/02/03 与 M5-WP01 既有套件
      原样通过（`RegistryCmd` 新增变体对 JSON 解码向后兼容）。
- [ ] **基准（T07）**：RouteQuery 往返 P50/P99（loopback）+ 10⁴ 路由行全量
      握手交换吞吐实测登记 `docs/reports/bench/M5-WP02-federation.md`。

## 风险与开放问题

- **联邦口无认证**：与 M3 raft 口同姿态（v0.1 局域网假设）；iroh 通道替换
  TCP 联邦口 = 首选演进路径（version 字节已留位），届时设备/联邦统一走
  iroh 加密传输；外部审计（D2 OSCP）进场时重审。
- **全量交换的规模上限**：10⁴ 行 × ~100B ≈ 1MB/握手，5s 周期无压力；
  超 10⁵ 空间需增量协议（后续卡，触发条件写入 T07 报告）。
- **epoch 无租约语义**：owner 失联不会自动改判——接管必须显式 claim（人工
  或上层策略）；自动 failover 归后续（需先定 hub 存活判据，不在 v0.1）。
- **`RegistryCmd` JSON 兼容**：新增变体向后兼容（serde enum 默认外部标记）；
  M3 全套回归为验收线。
