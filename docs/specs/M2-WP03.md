# SPEC: M2-WP03 —— Merkle 对账：分级树 + 水位线快路径（P7）

版本: 1.0 · 状态: 批准 · 关联: M2-WP00、M2-WP01/02、properties.md P7、调研方案 §5.7 对账协议 · 上游: M2-WP02
负责人: @lead · 批准日期: 2026-09-19

## 动机

oplog 重放只在「行还在」时有效——ACK 裁剪、晚加入者、分区后重连都会让纯 oplog
传播出现状态缺口（WP01 已把多对端覆盖缺口显式推给本 WP）。对账协议以**状态**
（而非操作）为比较对象：Merkle 根不等 ⇒ 下钻分歧区间 ⇒ 双边修复。
快路径（oplog 水位互换）让稳态对账退化为 O(1) 消息。

## 契约

### 1. schema v8（只增）：对账基建

```sql
-- 本店 HLC 时钟顶（持久化）：修复 WP01 时钟随进程重启回退的潜在缺陷，
-- 也是「本机是否又产生了新写入」的对账判据
CREATE TABLE IF NOT EXISTS sync_clock (
    id  INTEGER PRIMARY KEY CHECK (id = 1),
    top TEXT NOT NULL
);
-- 水位：来自 device 的 oplog 行，本店已应用（或 LWW 裁决过）的最大键
CREATE TABLE IF NOT EXISTS sync_watermark (
    device   TEXT NOT NULL,
    space_id TEXT NOT NULL DEFAULT 'default',
    last_hlc TEXT NOT NULL,
    PRIMARY KEY (device, space_id)
);
```

- `Store::open` 时从 `sync_clock` 恢复内存时钟；`record_oplog` / `record_oplog_raw`
  推进时钟后同步落盘（单调 UPSERT）。
- `set_watermark` 单调（仅接受更大键）；`watermarks()` 全表导出（快路径互换用）。

### 2. 分级 Merkle 树（graph 层，叶 = 状态而非操作）

- 叶集合三类（与 P6 收敛口径一致的可观察状态）：
  - entry：key = path，叶哈希 = blake3(`E␟path␟kind␟content_id␟owner_device`)；
  - tag：key = `tag/{id}`，叶哈希含 name/color/deleted——**不含 updated_hlc**
    （水位是簿记，不进状态比较，否则 LWW 落选方的根永不收敛）；
  - entry_tag：key = `link/{tag_id}␟entry_path`，叶哈希含 deleted（同理不含水位）。
- 分级：叶哈希（blake3 hex）前缀分桶——L1=4bit(16)、L2=8bit(256)、L3=12bit(4096)；
  桶哈希 = blake3(桶内叶哈希升序拼接)。全量扫叶即时计算（10⁵ 叶 ≈ 亚秒级，
  增量树留待 KPI 不达标再做——YAGNI）。
- API：`Store::merkle_root() / merkle_buckets(bits) / merkle_keys_in(bits, prefix)`。

### 3. 对账协议 `partisync-sync::reconcile`

```rust
pub struct ReconcileStats {
    pub rounds: u32, pub fast_path: bool, pub converged: bool,
    pub repaired_a: u64, pub repaired_b: u64, pub conflicts: u64,
}
pub async fn reconcile(a: &Store, b: &Store) -> Result<ReconcileStats>;  // max_rounds=16
```

**快路径（声音性条件——本 SPEC 的关键裁定）**：互换双方的水位表与时钟顶，
当且仅当覆盖相等才可跳过慢路径：

> ∀d ∈ origins(a) ∪ origins(b)：Seen_a(d) == Seen_b(d)，且 Seen_b(a) ≥ top(a)、
> Seen_a(b) ≥ top(b)。

依据：应用是 HLC 全序下的确定性折叠（含 LWW 裁决分支），覆盖相等的操作多重集
⇒ 状态相等（P6）。**只比 a↔b 双向水位不足以跳过**——第三方经中继落在单侧的
状态差异会被漏检（假阴性）；必须全 origin 覆盖相等。
水位可能因 `recv` 合并过冲而保守失效（快路径不触发，退化为根比对）——正确性不受影响。

**慢路径**：根比对 → 分歧 L1 桶下钻 L2 → L3 → 叶桶内按键差分修复：

- 仅单侧存在的叶 → 对侧按行应用（entry 走 `apply_remote_entry`；
  tag/link 走 `apply_remote_tag*`，以行上 `updated_hlc` 为 LWW 键——墓碑行照常同步，防复活）；
- 双侧同 key 不同值：
  - 属主不同 → 双向各应用对方行（保留两者，冲突改挂 + 血缘落档，P11 语义同 oplog 路径）；
  - 属主相同 → **属主行权威**（另一方就地更新）；
  - 属主为第三方 → 复合键字典序决胜（确定性收敛优先，人工仲裁归后续 WP）；
- 修复迭代至根相等或 `max_rounds`（冲突副本传播需 3 轮，16 充分冗余）。
- 收敛后落水位：`a.set_watermark(b, top(b))`、第三方 origin 取双侧 Seen 最大值
  （状态相等 ⇒ 覆盖合并为真）。

**push 记账**：`push_opts` 应用批次后，按行 `origin_device` 单调推进对端水位
（批内该 origin 最大键）——稳态 oplog 同步后，快路径即可生效。

## 验收标准（可执行）

- [ ] **P7（随机差分注入）**：proptest 构造两节点随机分歧状态（entry/tag/link
      随机增删改、oplog 零同步或部分同步）→ `reconcile` 后全量可观察状态
      （entry 集合 + tag 集合 + 链接集合，含墓碑语义的存活投影）完全等价；
- [ ] **晚加入者**：A 产生变更并 push 给 B（A 侧 oplog 被 ACK 裁剪）→
      C 空库加入，与 B 对账 → C 状态 == B（纯 oplog 路径不可能，Merkle 兜底）；
- [ ] 快路径：全量 bisync 后 `reconcile` 返回 `fast_path=true` 且零修复；
      人为注入单侧差异后 `fast_path=false` 且收敛；
- [ ] 分歧下钻覆盖：注入的差异必使根不等（无假阴性的对偶面——树根对差异敏感，
      blake3-256 碰撞概率为公认可忽略界）；
- [ ] 时钟持久化：Store 重开新写 oplog 键严格大于关闭前（回归 WP01 重启回退隐患）；
- [ ] push 记账：push 后对端水位 == 批内该 origin 最大键（单调）；
- [ ] 回归：P6/P11 全绿；fmt/clippy/test 全绿。

## 非目标

空间级多树（v1 单 default 空间）；内容块级差异到 ChunkPlan 的落位（WP05）；
网络化对端（WP04 前同进程双 Store）；对账并发调度（单对端串行）。

## 风险与开放问题

- 全量扫叶 O(N)/轮 × 最多 16 轮：10⁵ 叶收敛基准 <5min KPI 有充足余量；
  增量树为后续优化项（规格已声明非目标）；
- 快路径的覆盖相等条件在第三方中继场景偏保守（水位过冲即失效）——
  退化为根比对，正确性不受影响，实测后按需放宽；
- 叶哈希不含 updated_hlc：LWW 落选方的「状态相同但水位不同」不触发下钻——
  这正是期望行为（水位非可观察状态）；
- entry 无 per-row HLC，属主权威 + 字典序决胜已保证确定性；若未来引入
  非 LWW 语义的 entry 字段，需重审本节。
