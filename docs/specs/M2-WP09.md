# SPEC: M2-WP09 —— 混沌测试床：分区/断网/时钟混乱/崩溃恢复

版本: 1.0 · 状态: 批准 · 关联: M2-WP00、properties.md P8/P6/P7、调研方案 §6.3、§5.7 事件管线
负责人: @lead · 批准日期: 2026-09-19

## 动机

同步核 P6/P7 是单进程模型测试已证——但真实多设备场景下：网络分区导致长期离线、
时钟混乱（HLC 墙钟回拨）、进程崩溃在 oplog 落盘与 broadcast 之间的窗口、
断网 24h 重连后的收敛。WP09 提供自动化测试床把 WP01–07 的属性放进「可失败环境」。

v1 不引入 Docker / 网络仿真框架——测试床用 Rust 进程内**模拟器**实现：
- 时钟混乱：注入 HLC 墙钟偏移
- 进程崩溃：failpoint（事务边界 + 关键行）
- 分区/断网：路由表（节点 ↔ 节点之间的「连接」可关闭/恢复）
- 「三节点」用三 in-memory Store 实例 + 模拟器路由表

## 契约

### 1. 模拟器 API `partisync-sync::chaos::Chaos`

```rust
pub struct ChaosSim {
    nodes: HashMap<String, Store>,
    routes: HashMap<(String, String), bool>,  // (from, to) ⇒ enabled?
    clock_skew_ms: HashMap<String, i64>,      // 各节点时钟偏移
}

impl ChaosSim {
    pub async fn new(devices: &[&str]) -> Self;
    pub fn node(&self, dev: &str) -> &Store;
    /// 关闭/打开两节点之间的连接（模拟分区）
    pub fn set_partition(&mut self, a: &str, b: &str, open: bool);
    /// 注入时钟偏移（ms）
    pub fn set_clock_skew(&mut self, dev: &str, skew_ms: i64);
    /// 模拟 push——若两节点之间连接关闭则 no-op
    pub async fn push(&mut self, from: &str, to: &str) -> Result<SyncStats>;
    pub async fn reconcile(&mut self, a: &str, b: &str) -> Result<ReconcileStats>;
}
```

### 2. 故障矩阵

| 故障 | 注入方法 | 不变量验证 |
|---|---|---|
| 长期分区（≥24h 等价模拟） | 关闭 A↔B 连接 N 轮（推进时钟 N×1h 后恢复） | 重连后 reconcile 收敛 |
| 时钟混乱（回拨 1h） | set_clock_skew 注入负偏移 → 触发 HLC recv/tick 路径 | 后续同步不引入回退 |
| 时钟前推 1h | set_clock_skew 注入正偏移 → 新键严格更大 | P6 不受影响 |
| 进程崩溃（oplog 落盘前） | failpoint：truncate oplog 表模拟事务未提交 | P8 重放路径收敛（journal 已提交侧） |
| 节点宕机→重启 | 关闭节点的所有连接 → 推进时钟 → 重连 | 内容/状态等价 |
| 三节点非对称分区（A↔B 通、B↔C 通、A↔C 断） | set_partition 链路 | 中继路径保持 P6 |
| 高速连续 push（100 轮） | 高频 push + reconcile 交替 | 无死循环（reconciled rounds ≤ max_rounds） |
| 混沌混合（多故障并发） | 组合上述 | P6 + P11 + P7 不变量仍成立 |

### 3. failpoint 设计

- 命名：`failpoint::set("oplog.before_insert")` / `failpoint::off(...)`；
- 通过环境变量 `PARTISYNC_FP=oplog.before_insert` 启用；
- v1 实现：`failpoint` 模块暴露 `check(name) -> bool`，被调用点散布——`journal.rs`
  / `Store::record_oplog` / `Store::record_oplog_raw` 关键路径各 1 处；
- 测试断言可通过调用方控制 failpoint 注入。

### 4. v1 简化

- 不引入 tokio::time::pause——测试以逻辑时钟为主（毫秒级 skew 可控制）；
- 不引入完整网络栈模拟——bisync/reconcile 仍走「同进程双 Store」路径，
  chaos 仅控制是否调用 push/reconcile；
- 故障覆盖率：执行方案 §6.3「断网 24h 重连收敛」是核心——v1 通过时间快进 + 多次
  push 模拟「长时间累积差异」。

## 验收标准（可执行）

- [ ] 分区恢复：断 A↔B → A 写入 → B 写入 → 重连 → reconcile ⇒ A↔B 状态等价；
- [ ] 时钟回拨：注入 -3600s skew → 后续 push 不引入 HLC 回退；
- [ ] 时钟前推：注入 +3600s skew → 新键严格更大（LWW 大者胜）；
- [ ] oplog 落盘前崩溃模拟：truncate sync_oplog → journal 重放后状态等价（P8 守恒）；
- [ ] 三节点非对称分区：中继路径保证 P6（A=C 路径通过 B 中继到达）；
- [ ] 高速连续 push + reconcile：100 轮无死循环（reconcile rounds 有界）；
- [ ] 混沌混合：分区 + 时钟混乱并发 ⇒ P6/P11/P7 不变量仍成立；
- [ ] 零回归：所有 133 测试通过；fmt/clippy/test 全绿。

## 风险与开放问题

- failpoint 散布点是侵入性修改——最小化（仅 2-3 处）；
- 时间快进依赖 `tokio::time` 而非真实挂钟——「24h」等价为 24×60×60×10⁹ ns 累计
  偏移（用 sleep 或快进 3600s skew）；不依赖系统时间跳变（系统时间跳变会破坏
  HLC 内部 wall 假定）。
