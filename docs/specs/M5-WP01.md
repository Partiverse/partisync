## 0. 背景与问题定义

在 M4-WP04 中，设备到 Hub 的 blob 传输基于 `iroh-blobs 1.2.0` 的 QUIC `execute_push`。其传输层语义为 **fire-and-forget**：
设备端调用 `send.finish()` 后立即返回，不等待 Hub 端完成 CAS 落库及元数据关联。若设备在此时过早关闭连接，Hub 侧因连接中断可能丢弃未完全落盘的数据，导致数据不一致（丢失）。

本工作包（M5-WP01）正式实现基于 QUIC 单向流的 **UploadAck (v0x01)** 协议，确保：
1. Hub 端在 blob 数据验证通过且成功写入 ChunkStore（refcount+1）后，主动向设备端推送 35 字节定长 UploadAck 确认帧。
2. 设备端维护可靠确认机制（`UploadAcker`），在确认收到指定 Hash 的 ACK 前保持连接存活；支持超时检测与状态判定。
3. 提供完备的 loopback 集成测试覆盖基础 push、多 blob 连续推送、以及超时异常场景。

## 1. 协议帧格式与状态定义

### 1.1 帧格式（35 Bytes 定长）
```text
[1B Version = 0x01][1B Type = 0x02][32B Blake3 Hash][1B Status]
```
- `version`: `0x01`（`UPLOAD_ACK_VERSION`）
- `type`: `0x02`（`UPLOAD_ACK_TYPE`）
- `hash`: 32 字节 Blake3 Hash（对应 `iroh_blobs::Hash`）
- `status`: 1 字节状态码（`UploadAckStatus`）

### 1.2 状态码定义
- `0x00 Accepted`: Hub 端成功完成校验与 CAS 落盘（refcount 递增）。
- `0x01 Duplicate`: 块已存在，去重跳过，保证幂等。
- `0x02 Rejected`: 校验失败（Hash 不匹配或校验错误）拒绝接收。
- `0x03 Retrying`: Hub 暂时繁忙或资源受限，请求设备端退避重试。

## 3. 验收标准
1. **协议不变量**：所有进入 CAS 的 blob 均有且仅有一条对应的 `Accepted` 或 `Duplicate` 确认帧回传给设备。
2. **连接稳定性**：设备端使用 `expect_ack` 阻塞等待直至 ACK 返回或超时，消除连接过早关闭导致的数据丢弃风险。
3. **CI 门禁**：`cargo test -p partisync-hub --test m5_wp01` 保持 100% 绿灯。
