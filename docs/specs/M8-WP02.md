## 1. 动机

全仓至今 **0 个 git tag、无 release workflow**，执行方案 §5.4 的 G4
（签名 + SBOM）从未实跑——「基建底座」定位下没有一个签名可分发的
对外版本。这是前瞻计划盘点的 G1 结构性空白：一切企业/生态/分发叙事
（Hub 治理、扩展 registry、桌面分发）的前提是先存在一个可验证来源、
可审计依赖、可复现构建的产物面。

不实跑则发布能力停留在 CI 假设上：签名密钥保管、SBOM 生成、changelog
流程这些**只有真实打一次 tag 才会暴露的工程问题**继续隐藏，M9 的
签名 registry 与 MCP 远程 server 无产物可签。

## 2. 契约（草稿级，批准即冻结）

### 2.1 版本口径（M8-WP00 §2 拍板项③随本 SPEC 批准落锤）

- 首个 tag：`v0.1.0-alpha`（semver pre-release 语义）；
- 产物面三件：`partisync-cli`（linux x86_64 tar.gz + macOS aarch64
  tar.gz）、`partisync-hub`（linux x86_64 tar.gz）、`partisync-desktop`
  （macOS aarch64 .dmg，Tauri bundler）；Linux 桌面包评估不入首版
  （§4 非目标）。

### 2.2 签名与密钥保管

- minisign 式工程签名（执行方案 §5.4 口径）：每个产物附 `.minisig`
  签名 + SHA256SUMS 清单；公钥入仓（`docs/release/` + README 验证
  说明），私钥**不出 CI**（GitHub Actions secret 注入）；
- 密钥双人保管：私钥生成流程与分持份额登记 `docs/release/key-custody.md`
  （人工程序项，AI 只起草流程文档不接触密钥材料）；
- 新依赖（minisign crate 或 CLI 工具链）→ **ADR + cargo deny**（铁律 8），
  实施首任务完成。

### 2.3 SBOM 与可复现构建

- `cargo auditable` 构建包装：依赖清单嵌入二进制，Release 附生成的
  SBOM 导出；
- 可复现构建口径：`cargo build --locked` + rust-toolchain.toml 钉版 +
  runner 环境记录；**双构建 hash 对照**（CI 内独立两次构建产物
  SHA256 一致）；不可复现面（macOS codesign/dmg 时间戳等）如实登记
  已知偏差清单，不假绿。

### 2.4 release workflow 与 changelog

- `.github/workflows/release.yml`：tag push 触发 → 三平台构建 → 签名
  → SBOM → checksums → GitHub Release 发布；
- changelog：AI 从 PR 集（`git log` + Task-ID 追溯）自动起草，人终审
  后入 Release notes（执行方案 §5.4 判例）。
