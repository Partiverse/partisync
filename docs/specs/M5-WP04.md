## 动机

WP02 联邦路由 + WP03 分片并行扫描解决「全量在联邦规模下可行」；**增量路径**
仍是空白——云端每写一个对象若走全量 LIST 校准，10⁹ 条目代价不可接受（调研方案
§4.1：单前缀 5500 GET/s 上限）。云厂商各自提供事件流（S3 Event Notifications →
SQS / SNS / EventBridge、GCS Pub/Sub、Azure Event Grid、MinIO webhook），
KP 可对接 Kafka。WP04 交付 **统一 EventSource 抽象 + 三适配 + journal 协调**：
驱动 capture 链路，把云事件折叠到与本地 `notify` 同口径的
`EventKind::Created/Modified/Removed`，落 `graph::journal` 走既有的幂等
upsert 通路——与 WP01/WP03 完全解耦。

## 裁定总览

1. **位置与形状**：`partisync-sync/src/event.rs`（能力层向下依赖 provider/
   graph，方向合规）。核心三件套：`EventRecord{provider, space, path, kind,
   cursor, payload?}` + `EventSource` trait（poll 一批）+ `EventJournal`
   trait（与 WP03 同构 FileJournal 复用 save/load，零新增形态）。
2. **kind 折叠**：云端 `ObjectCreated:Put`/`ObjectCreated:Copy` →
   `Created`；`ObjectModified` 系 → `Modified`；`ObjectRemoved:*` →
   `Removed`。**折叠映射入 EventSource 实现内**，sync 侧只见统一枚举；
   各家差异由适配器 `map_kind()` 吸收。
3. **顺序保证（v0.1 单源单分片）**：单云端对象的事件流**保证单调**（S3
   顺序键、Kafka 单分区有序、webhook 单前缀）；本 WP 假定上游有序——跨
   分片/跨源一致性归后续（与 WP03 跨 hub 同口径）。
4. **checkpoint = cursor + processed_seq**（裁定 4）：每事件带 cursor
   （SQS receipt handle / Kafka offset+partition / webhook 时间戳+nonce）；
   应用成功 → 推进 record 更新；同一事件重投递（双消费/重试）靠 cursor
   **不可重入**（SQS delete / Kafka commit / webhook ack）保证 + 本地去重
   表（`journal.seq` 主键幂等 upsert）双保险。
5. **批量 + 超时**：poll 批次 ≤ 256 条 + batch deadline ≤ 5s（任一满即返）；
   `pending` 队列自 mpsc（同 WP03 协调协议）→ 应用 worker 自取——
   一台 hub 同时支持多 source（多 prefix / 多队列）。
6. **失败语义**：source 拉取失败重试 3 次（指数 backoff 250/500/1000ms）→
   计入 source fail counter + 续读下批（不阻塞其他 source）；应用失败（store
   upsert 抛 Err）= fail-fast 同 WP03 裁定 5。failpoint 命名点：
   `event.before_apply` / `event.after_cursor`。
7. **空间路由接入**：每条 EventRecord 带 `space`（从 object key 前缀 /
   event metadata 解析；webhook 配置静态指定）→ 经联邦视图
   `HubService::route_for(space)` 判断本 hub 是否持有（WP02 协定）；非
   本 hub 持有 = `Redirect` 不应用（仅记账），待上游 Worker 接管——
   v0.1 简化：**仅本 hub 持有空间的事件落 journal**（联邦面 worker 接管归
   后续卡）。
8. **CLI 入口**：`partisync event-drain --source <sqs|webhook|kafka> ...
   [--journal <path>] [--cursor <token>]`——常驻进程拉取 → journal →
   checkpoint 续跑。

## 契约

### 1. 数据模型

| 项 | 形态 |
|---|---|
| `EventRecord` | `{ provider: String, space: String, path: String, kind: EventKind, cursor: String, payload: serde_json::Value }`（path 无前导 `/`，同 `ListedNode`） |
| `EventSource` | `async fn poll_batch(&self, max: usize, deadline: Duration) -> Result<Vec<EventRecord>, EventError>`；`async fn commit_cursor(&self, cursor: &str) -> Result<(), EventError>` |
| `EventJournal` | `async fn save(&self, state: &EventJournalState)` + `load`（与 WP03 同构，复用 FileJournal 模板） |
| `EventJournalState` | `{ sources: HashMap<String, SourceCheckpoint> }`；`SourceCheckpoint { cursor: String, processed: u64, failed: u64, last_at_ns: i64 }` |

### 2. 错误集

```rust
pub enum EventError {
    /// 拉取/提交失败（IO/HTTP/Kafka broker）→ 重试+计入。
    Transport(String),
    /// 配置错误（凭证/endpoint 缺失）→ 不重试，进程退出。
    Config(String),
    /// 应用失败（store upsert 抛）→ fail-fast 透传。
    Apply(PartisyError),
}
```

### 3. 适配器职责（实现示例）

- `SqsAdapter`（aws-sdk-sqs）：`poll_batch` = `ReceiveMessage`
  MaxNumberOfMessages=10×26 批 + VisibilityTimeout；`commit_cursor` =
  `DeleteMessageBatch`。v0.1 仅签名 + 配置（依赖另立 ADR 触发）。
- `WebhookAdapter`（axum POST + HMAC 校验）：被动——不主动 poll，接收
  HTTP POST 写 channel；提供 `from_channel(rx)` 形态而非 trait 直接实现
  （v0.1 简化：stub channel + 测试桩）。
- `KafkaAdapter`（rdkafka）：partition consumer 异步流 → batch accumulator；
  `commit_cursor` = `store_offset`。

**v0.1 外部依赖策略**：SQS/Kafka SDK = 新顶层依赖，须 ADR（铁律 8）。
**v0.1 改走 mock + webhook adapter 落 axum**（axum 已是 workspace 既有
依赖，零新增）。SQS/Kafka 适配器留 trait 边界 + 测试桩，正式 SDK 接线归
后续 ADR 卡。

### 4. 调度器

```rust
pub struct EventDrain<S: EventSource, J: EventJournal> { /* source, journal, opts */ }
impl EventDrain { pub async fn run(space: &str) -> Result<Stats, EventError>; }
```

- 循环：poll_batch → 折叠空间路由 → 本 hub 持有 → 落 journal；cursor commit
  + checkpoint save（每批一记）。
- 终止：`shutdown_rx` 信号（CLI Ctrl-C 桥接）或 journal load 出 completed
  marker（一次性跑场景）。

## 验收标准（可执行，测试先行）

- [ ] **折叠映射正确**（S3→kind 单元测试）：webhook POST payload 各变体
      → `Created/Modified/Removed` 对应。
- [ ] **去重幂等**：同 cursor 重投递两次 → journal upsert 主键去重，
      seq 不重复。
- [ ] **断点续传**：mock source 在 poll N 批次后中断（failpoint panic）
      → 新 drain load 账本 + cursor 续传 → 续集齐；失败 source 计数
      一致。
- [ ] **失败隔离**：source 拉取重试耗尽 → 计入 failed → 下批继续；
      apply 失败 → fail-fast 返 Err。
- [ ] **空间路由闸**：非本 hub 持有空间事件 → 不落 journal（仅记账）；
      本 hub 持有空间事件 → 落。
- [ ] **CLI 续跑幂等**：常驻 1 轮 kill NOK；同 journal 二轮启动 →
      增量 0。
- [ ] 回归：fmt/clippy/test 全绿；M3/M5 既有套件原样通过。
- [ ] **基准（T05）**：mock source 1k 事件/poll 实测吞吐与 P99 commit
      延迟；webhook receiver 并发 1000 POST 落盘时延分布。

## 风险与开放问题

- **SQS/Kafka SDK 引入**：v0.1 stub 满足验收，正式 SDK（aws-sdk-sqs /
  rdkafka）属新增顶层依赖，须 ADR（铁律 8）后再启卡；本规格不预先授权。
- **跨源顺序与去重**：v0.1 单源单分片假定上游有序——多源合并一致性归
  后续（联邦面 + 跨前缀顺序）。
- **webhook 安全**：HMAC 校验依赖云端密钥；v0.1 留 `secret` 配置位与
  `verify_signature` 助手，校验算法支持 S3 / MinIO（X-Signature-SHA256
  + X-Amz-Signature）——D2 OSCP 进场时重审。
- **EventSource 形态与 watch 协调**：本地 `watch` 经 std mpsc 回调，
  webhook 通过 axum；统一收敛在 mpsc 通道内后接调度器即可，不另立
  EventSink——与 WP03 sink 同位置。
