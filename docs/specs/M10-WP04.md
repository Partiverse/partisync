## 1. 动机

可验证记忆层一期（M9-WP02，ADR-0029）交付了内容寻址幂等写 + Merkle
inclusion proof + MCP 三工具，但生命周期面是单向的：**「写→证明」而无
update/delete/GC**——`deleted` 列仅预留恒 0（schema.sql:226），oplog
只有 `("memory","upsert")` 应用臂（session.rs:229）。写错的事实无法撤
回、过期记忆无法清理，编辑/删除 UI 在桌面两侧 SPEC 双双挂「tombstone
前置」（M10-WP02/M10-WP03 §4）；生命周期缺口是二期「守住零竞品空位」
的点名动作（M9-report §8-5、M10-roadmap-proposal §6-NB2）。ADR-0029
重新评估条件明示：删除/GC 落地时须增补修订登记（tombstone 叶口径评估
根稳定性）——本 WP 落锤。

第二笔债：**NB5 CAS 内容重组缺口**（M9-WP03-T06 登记，M9-report §5 债
表 ⏳ 行）。大文件分块入库时 `put_chunks` 返回的 chunk hash 列表在
indexer.rs:192 被 `let (_, r)` 丢弃，entry 只存 Merkle 根（schema.sql:40
）——列表未持久化，content→bytes 不可重组；reindex 的 CAS 回退仅覆盖
单块小文件，大文件命中计 read_errors（reindex.rs:86）。schema v1 注释
本就把 chunk 表列为「归属后续工作包」，本 WP 清偿。

第三件：**语义向量检索条件评估**（M9-WP02 §4 条件触发；M10 拍板 #2
「tombstone 先行 + 向量评估随行」）。底座已在仓：fastembed（`ai-embed`
feature，partisync-ai/Cargo.toml:12，BGE-M3 768d，ADR-0018）+ usearch
HNSW（partisync-index/src/search/vector.rs，TextDense 768d Cos）+ hybrid
现成——评估件只做选型对比与触发条件落锤，**只评估不实施**。

不做本 WP：生命周期缺口使「可验证记忆」停留在只增不减的日志面，写错
即永久污染检索结果；NB5 不清则 reindex 对大文件持续 read_errors；
向量评估缺位则二期检索深化无决策依据。

## 2. 契约

### 2.1 tombstone 生命周期（T01/T02/T03；ADR-0029 修订登记随 T01）

- **memory_delete(memory_id)：软删除墓碑**。`deleted=1` + 行 hlc 推进
  + 同事务 oplog `("memory","delete")`（payload 恰含 memory_id）+ 根
  快照刷新。**拍板（ADR-0029 修订登记内容）：墓碑行留在承诺集——软删
  除不改根值**。依据：叶编码不含 deleted（memory.rs:113），墓碑不动叶
  → 根天然稳定；透明日志语义 = 删除不抹除承诺，被删记忆仍可出示
  inclusion proof（防删史）。备选「可见集=活行、删除动根」否决：改叶
  编码破坏 P20 确定性存量兼容，且丢失删史承诺。
- **memory_update(memory_id, content?, tags?, metadata?)**：id 内容寻
  址 ⇒ 更新必换身份 = **同事务墓碑旧 id + 写入新行**（新 id 由新
  canonical 内容派生）；canonical 等价（同 id）→ no-op 返回原 id；
  目标 id 不存在或已墓碑 → 工具级错误（不静默建行）。
- **复活语义**：`memory_write` 命中墓碑行（同 id）→ 复活（deleted=0 +
  hlc 推进 + 根刷新），返回 `deduplicated=false`；活行幂等不变
  （store.rs:2100 既有路径）。
- **同步**：session.rs 新 `("memory","delete")` 应用臂——delete hlc >
  行 hlc → 墓碑落位，否则晚到拒绝（沿 `("tag","remove")` 判例
  session.rs:215-221 与 tag 墓碑「LWW 水位拒晚到」口径 store.rs:1130
  ）；中继沿 relay 既有。证明树叶序不变（P20-a 输入集=含墓碑全集，
  叶按键升序）。
- **memory_verify(memory_id) 响应增 `deleted: bool`**：墓碑行 proof
  仍通过，凭旗标知实态；无 id 全检报告增 `tombstones` 计数
  （memory_count 口径 = 含墓碑承诺集规模，诚实透出）。
- **memory_gc（T03，硬清除）**：判据 = 墓碑行 hlc（delete op 水位，
  定宽 hex 字典序=时间序，store.rs:1238 口径）早于截止水位（默认保留
  期 30 天；如需显式列可 additive 增 `memory.deleted_ns`，随 v18）。
  物理删行 → 根重算（**GC 动根**，与软删不动根对照）+ FTS 随 AFTER
  DELETE 触发器自动清（schema.sql:355-357）+ memory_count 更新。GC
  本地维护动作不产 oplog（墓碑 op 已传播）；CLI 入口 `partisync
  memory-gc [--db <path>] [--retention-days N]`。
- **P20 措辞注记**（properties.md 随 T01 增补，不新设 P 编号）：承诺
  集 = memory 全体行（含墓碑）；软删除不动根，GC 动根；a/b/c 语义
  在该口径下零回退。

### 2.2 CAS 内容重组清偿（T04，NB5）

- **schema v18（additive-only 幂等，沿 v16/v17 判例）**：新表
  `content_chunk(content_id, seq, chunk_hash, PRIMARY KEY(content_id,
  seq))`——content_id 粒度（同 content 多 entry 共享行集，写入幂等
  INSERT OR IGNORE）。
- **写入方**：indexer 分块站点（indexer.rs:192）改取 `put_chunks`
  返回的 hash 列表（cas/store.rs:248 签名 `(Vec<String>, String)`）
  落表，与 entry.batch 同事务；「内容未变跳过重分块」既有逻辑
  （indexer.rs:183-187）不变。
- **读出方（重组 API，graph 内组合）**：`content_chunk_hashes(
  content_id)`（seq 升序）+ 重组 helper——按列表经 CAS 取块 concat，
  校验 `blake3(bytes) == content_id` 且 `chunk_root(list) ==
  entry.chunk_root`；**任一块 CAS 缺失 → 显式 Err，不静默截断**。
- **reindex 接线**：大文件回退路径（chunk_root 非空）优先走重组读出；
  列表缺失 = 存量数据（落表前入库），**不可回填**，维持 read_errors
  计数（reindex.rs:86 债注释摘除）。**同步面零变更**：chunk 清单是
  CAS 派生数据，不入 oplog/payload。
- **新不变量 P22**（CAS 内容可重组承诺，登记随 T04 走
  partisync-property-registry，**登记先于测试代码**）：
  (a) 落表完整——`chunk_root(list) == entry.chunk_root`；
  (b) 可重组——按列表取块拼接结果 `blake3 == content_id`；
  (c) 缺块显式失败——任一块 CAS 缺失必 Err，绝不返回部分字节。

### 2.3 语义向量检索条件评估件（T05，只评估不实施）

交付 `docs/reviews/M10-WP04-memory-vector-eval.md`，六问必答（零代码
零依赖变更；结论供后续 WP 立项引用，本 WP 不落实施件）：

1. **既有件盘点**：fastembed `ai-embed`（BGE-M3 768d，ADR-0018 门控）
   + usearch VectorStore（TextDense 768d Cos，碰撞口径 vector.rs:9-14）
   + hybrid 现状——零新增依赖可走多远；
2. **三方案对比**：复用 TextDense 新 key 域 / 独立 memory 向量
   artifact / sqlite 暴力扫（叶量 10⁵ 口径）；
3. **P20 承诺边界**：向量与 embedding 不进叶编码、不进承诺；
4. **公共面变更路径**：`memory_search` 增语义参数/新工具 = gateway
   公共工具面变更 → pre-merge-safety R2 + ADR 触发条件列明；
5. **成本/性能口径**：本地嵌入计算 + 索引增量维护 + 查询延迟预估；
6. **拍板建议 + 实施触发条件**（含是否超出 ADR-0018 锚定 → 新 ADR 与否）。
