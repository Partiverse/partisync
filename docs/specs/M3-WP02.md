## 动机

WP01 交付单写者元数据平面（10⁷ 实测：稳态写 109k/s、LIST p99 36.1ms、盘上
182.3B/条目）。WP02 加复制与一致：每 range 分片一组 Raft（M3-WP00 工作包图），
领导者转移/选举演练、故障切换 <10s 无损（关门 KPI），单条目线性一致语义文档
（钉子级，双人全审）。本 WP 只做复制与一致；对账（WP03）、数据面（WP04）、
检索（WP05）、规模验证（WP06）不动。

## 裁定总览（待 G0 批准的关键决策）

1. **每分片一组 raft，成员静态配置**：v0.1 每组 3 成员（可配 5），节点集固定、
   无自动扩缩容（auto-scaling 留 WP06 后）；「路由表可替换」插桩点（WP01 §2）
   兑现为 `shard_id → {node_id → raft 组句柄}` 的组注册表（持久化 meta
   keyspace）。
2. **openraft 0.9 storage-v2 适配 fjall**（ADR-0013）：每组的 raft 日志与
   状态机映射到同一 Database 的独立 keyspace；已 ACK 写入不丢（关门 KPI）
   由 raft 日志 + fjall 原子批承接。
3. **keyspace 收敛先行**（T02，WP01 风险条目清偿）：256 哈希分片收敛为共享
   keyspace + `shard_id` 键前缀；range 分区同理；openraft 组 keyspace 用
   `{pid}` 前缀共享实例。目标把 Database open 从 12.8s（256+ keyspace 逐个
   fsync，m3-wp01-kpi.md）压回秒级—— raft 组 ×log/sm 叠加后不收敛不可运营。
   行为契约不变（WP01 全部测试原样通过 = 验收线）。
4. **网络层零新依赖**：tokio `TcpStream` 长连接 + 手写紧凑帧
   （`u32 len + u8 type + body`）；openraft 信封（Vote/LogId 等）走 serde_json，
   Entry 载荷沿用 WP01 紧凑二进制编码（RaftTypeConfig 的 AppData 为
   newtype-over-bytes，不过 JSON）。D3「iroh 真实网络层」继续不在 M3 范围。
   吞吐若被 JSON 信封拖累（T07 基准实测），信封换紧凑编码为本地优化、不动协议。
5. **写路径 = leader 串行，读路径 = ReadIndex 线性一致**：所有写经 leader
   append+复制后应用（WP01 单写者语义由 raft 天然保持）；get_entry/list_children
   的读走 openraft 0.9 线性一致读入口（ReadIndex 语义，方法名进场核实）。
   WP01 §5 底稿（跨平面投影、无事务）在复制层原样保持——每分片各自线性一致，
   跨分片不做分布式事务。
6. **分裂 × 复制耦合**：split 仅 leader 执行；搬移原子批作为源组 raft 日志
   条目复制（崩溃恢复 = 日志重放，WP01 协议不变量原样成立）；新分区组以空
   日志 bootstrap，其初始数据由控制面在源组日志覆盖搬移后按序写入新组日志。
   分裂期间路由由组注册表驱动双读合并视图（WP01 §3 语义不变）。本耦合的
   崩溃矩阵进钉子清单（T06 语义文档双人全审）。
7. **投影与权威平面的复制粒度**：entry 行与 children 行是同一 raft 组内
   两个状态机 section（同一 log，各自应用），保证跨平面投影的复制顺序一致
   （WP01 put/rename/remove 的「行先投影后」顺序在应用侧逐条重放）。

## 契约

### 1. keyspace 布局（收敛后物理模型）

| keyspace | 键 | 内容 |
|---|---|---|
| `m-entry` | `shard_id(1B) ␟ entry_id(16B)` | entry 权威行（256 前缀共享） |
| `m-child` | range 分区键（收敛后键序不变） | children 投影行 |
| `m-meta` | WP01 `t-meta` 语义 | 分区表 / 组注册表 |
| `r-{pid}-log` / `r-{pid}-sm` | openraft 布局 | 组 {pid} 的日志 / 状态机 |

- 分区→组的映射：`{pid} → raft_group`，节点集静态；组注册表持久化于 `m-meta`。

### 2. Hub API（WP01 §4 签名不变，语义升级）

- `Hub::open` 增加节点身份与组拓扑参数（构造期注入，v0.1 不做动态成员）；
- 全部读写签名不变：写=线性一致（leader log committed），读=线性一致
  （ReadIndex）；WP01 测试套件（单节点组、成员={self}）原样通过 = 回归线。

### 3. 一致性语义（WP02 文档的骨架，钉子）

- 单分片内：写线性一致（committed 后应用），读线性一致（ReadIndex，不读旧值）；
- 跨分片：无事务（WP01 §5 裁定保持），投影暂缺窗口 = 复制延迟 + 崩溃间隙，
  WP03 对账收口；
- 故障切换：已 ACK 写入不丢（raft 承诺）；ACK 前崩溃的写 = 未提交（客户端
  超时语义，与 WP01 v0.1 无事务口径一致）。

## 验收标准（可执行，测试先行）

- [ ] **回归**：WP01 全部验收测试以「单节点组」拓扑原样通过（含读时修复、
      failpoint 崩溃一致性、投影一致性 proptest）；
- [ ] **故障切换 <10s 无损**（关门 KPI）：3 节点组 kill -9 leader → 新 leader
      当选 + 服务恢复 <10s；切换前已 ACK 的写入全部可读（确定性测试 + 演练记录）；
- [ ] **领导者转移**：主动 transfer <5s，转移窗口写延迟有界（演练记录）；
- [ ] **线性一致读**：并发写后读单调（proptest）；follower 经 ReadIndex 读
      不返回旧值；写后读自己写（read-your-writes）成立；
- [ ] **复制导入基准（T07）**：3 节点组 10⁶ 条目复制导入吞吐实测登记底稿
      （对照 WP01 单机 109k/s 定衰减系数；10⁹/24h 外推口径归 WP06）；
- [ ] **分裂在复制下正确**：leader 触发 split、搬移批经日志复制；follower
      不触发分裂；split 期间 kill leader → 重选后协议收尾（failpoint 复用
      WP01 三注入点 × 组拓扑矩阵）；
- [ ] **keyspace 收敛**：Database open ≤2s（对照 12.8s）；WP01 基准三线
      （吞吐/LIST p99/盘上预算）不回退超 10%；
- [ ] 回归：fmt/clippy/test 全绿；deny 零新增白名单外条目（ADR-0013 进场复核）。

## 风险与开放问题

- openraft 0.9 方法级 API 未预写（铁律 8）：ReadIndex 入口、成员变更入口、
  storage-v2 开关语义均以 0.9.25 文档/源码进场核实，必要时修订本 SPEC（记录）；
- keyspace 收敛动 WP01 物理布局——行为契约不变的验收线是 WP01 全量测试
  原样通过；若收敛击穿性能基线（>10%），回退为按需惰性打开 keyspace
  （open 时只开 meta，首访再开数据 keyspace），行为不变；
- JSON 信封吞吐：T07 基准实测决定是否换紧凑信封（本地优化，协议不动）；
- 分裂×复制耦合的崩溃矩阵是本 WP 最高风险面（裁定 6）：failpoint 注入点
  复用 WP01 三协议点 + 组生命周期点，测试先行；语义文档双人全审为合入门槛；
- 单写者→多节点后 WP01 的「进程内 &self 独占」假设失效：并发面收窄为
  raft 内部串行 + ReadIndex，T06 文档显式重审 WP01 §5 的单写者裁定（钉子）。
