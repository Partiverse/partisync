# SPEC: M2-WP06 —— 占位符骨架同步与按需 hydrate

版本: 1.0 · 状态: 批准 · 关联: M2-WP00、调研方案 §5.7（事件管线即时/批量通道）、执行方案 §6.3
负责人: @lead · 批准日期: 2026-09-19

## 动机

M2-WP02 已能把「对方有，我没有」的 entry 通过 oplog 投到本端——但内容体未到位
（apply_remote_entry 已支持 content=null 缺位）。WP06 让「仅有元数据（path/
size/mtime/owner）的骨架」能独立同步，按需 hydrate 内容：避免手机收下整
G 工作集后再决定要不要，节省 LAN 带宽与存储；也使 NAS 媒体库与笔记本
工作集并存而不互踩。

## 契约

### 1. schema v9（只增）

```sql
-- entry.state 由 0=materialized 扩到 0=materialized, 1=placeholder
ALTER TABLE entry ADD COLUMN content_hydrated_at_ns INTEGER;  -- 上次内容到位时间戳
ALTER TABLE entry ADD COLUMN pin_count INTEGER NOT NULL DEFAULT 0;  -- 本地 pin 引用数
CREATE INDEX IF NOT EXISTS idx_entry_state ON entry(state);
```

### 2. Store API

```rust
/// 元数据已就位、内容待 hydrate（占位符）——M2-WP06。
pub async fn add_placeholder(&self, parent_id: Option<&str>, name: &str, path: &str,
    size: u64, mtime_ns: u64) -> Result<String, PartisyError>;

/// hydrate：内容到位后清 placeholder 标记，记时间戳。
pub async fn hydrate_entry(&self, path: &str, content: (&str, u64)) -> Result<(), PartisyError>;

/// pin/unpin（用户显式保留）：pin_count > 0 的条目永不被回收（WP08）。
pub async fn pin(&self, path: &str) -> Result<(), PartisyError>;
pub async fn unpin(&self, path: &str) -> Result<(), PartisyError>;
```

### 3. 同步语义（与 WP02 兼容）

- oplog payload 携带 `state` 字段；placeholder 行同步到对端 → 对端以占位符形式
  接收（content_id = NULL、size = 占位 size、state = 1）；
- `apply_remote_entry` 兼容 placeholder：保留 content 字段缺位逻辑；
- hydrate 不广播——hydrate 是本端本地动作（内容已通过块传输到位，与元数据
  同步解耦）。v1 简化：「骨架同步」=元数据 + oplog；「按需 hydrate」=本地调用
  hydrate_entry。

### 4. 非网络化

WP06 不引入网络协议；hydrate 由 WP05 块传输完成后调用 hydrate_entry。

## 验收标准（可执行）

- [ ] `add_placeholder` 创建 state=1、content_id=NULL 的条目；hydration 后
      state=0、content_id 落位、content_hydrated_at_ns 非空；
- [ ] pin/unpin 单调：重复 pin 不增计数；unpin 仅减一次（pin_count ≥ 0）；
- [ ] oplog 同步：a 创建 placeholder → push b → b 上 entry state=1、content 缺位；
- [ ] hydrate 后本端 state=0、content_id 落位、content_hydrated_at_ns 非空；
- [ ] 回归：P6/P11/P7 全绿；fmt/clippy/test 全绿。

## 非目标

按需 hydrate 的「智能」策略（LRU / 访问热度 / pin 自动绑定）——用户/调用方负责；
占位符回收策略（WP08 接管：基于 pin_count + 上次访问）；
骨架显示在 UI 中的差异（属壳层任务，M6 范围）。

## 风险与开放问题

- placeholder 内容缺位期间若用户尝试读 → 触发按需 hydrate（v1 由壳层处理，
  graph 仅暴露 hydrate_entry 与 state 状态）；
- size 在 placeholder 阶段已记录（来自对端元数据），hydrate 时 content.size
  应与 placeholder.size 一致——不一致即日志告警而非拒绝（v1 简化口径）。
